# 客户端 HUD 与交互架构设计（v0.8-v1.0 前端底盘）

状态：设计定稿，待实施
日期：2026-07-02
上游文档：`docs/superpowers/plans/2026-07-02-v0.8-v1.0-closed-beta-roadmap.md`、`docs/reviews/2026-07-02-fable5-code-review-report.md`（前端审查 + R4）
定位：后端有"引擎收编重复工作"的原则，本文是它的前端对等物。v0.8/v0.9/v1.0 的所有 UI 需求（装备对比、大厅聊天、离线报告、新手引导）都落在这个底盘上，而不是继续往单个 GameShell 里堆。

## 1. 现状问题与到 v1.0 的 UI 需求清单

现状：GameShell 单组件约 870 行、15 个 `useState`、4 个互不感知的弹窗布尔（审查评分 4/10）；无轮询（进度条冻结）；API 层丢弃错误码；键盘守卫只认输入框不认弹窗（C4，v0.7.1 已做最小修复）。

到 v1.0 要挂上来的 UI（按版本）：

| 版本 | 新增 UI |
| --- | --- |
| v0.8.0 | 行动进度自动刷新、统一错误提示、面板/弹层/快捷键底盘 |
| v0.8.1 | 背包装备区、装备对比面板、稀有度配色、掉落/升级反馈 |
| v0.8.2 | 第二区域切换、旧矿坑状态与事件日志过滤 |
| v0.9 | 大厅面板（在线列表/聊天/排行榜）、聊天输入、掉落广播流、离线世界报告、NPC 态度可视化 |
| v1.0 | 新手引导提示层、键位说明面板、错误/会话过期引导、可用性基线 |

不做整体设计，这些会把 GameShell 推到 2000+ 行和十几个互相踩踏的布尔。

## 2. 信息架构与 HUD 布局

桌面三区 + 一条输入栏的 MUD 面板式布局（延续现有风格，重排职责）：

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏 HUD（常驻）: HP | 饥饿 | Lv+XP条 | 铜币 | 位置 | 当前行动进度 │
├───────────────────────────────┬──────────────────────────────┤
│ 主区（场景层）                  │ 侧栏（面板区，tab 化）          │
│  - 地图网格 + 移动             │  [背包] [装备] [任务] [NPC]    │
│  - 场景描述                    │  [市场] [大厅*] [报告*]        │
│  - 事件日志（主叙事流，含掉落/  │  * v0.9 挂载                  │
│    升级/广播高亮）              │                              │
├───────────────────────────────┴──────────────────────────────┤
│ 输入栏: 聊天/命令输入（v0.9 起) + 键位提示                       │
└──────────────────────────────────────────────────────────────┘
弹层（唯一 ModalManager）: 装备对比 / NPC 对话 / 战斗详情 / 道具详情 / 确认框
```

设计规则：

1. **常驻信息只有顶栏**：生存状态（HP/饥饿）、成长状态（Lv/XP）、财富、当前行动。其余一切皆面板或弹层——屏幕预算是刚性约束，任何新功能默认进侧栏 tab，不得新增常驻区。
2. **事件日志是主叙事流**：掉落、升级、战斗结果、全服广播、传闻全部汇入主区日志（分类着色、可过滤），而不是各自开新 UI 区域。MUD 的灵魂是这条流。
3. **面板注册表（Panel Registry）**：侧栏面板以 `{ id, title, hotkey, badge?, component, visibleWhen? }` 注册，shell 只负责布局/切换/徽标。v0.9 的大厅、离线报告 = 注册两个新面板，不改 shell。这是前端的"内容驱动化"。
4. **弹层唯一管理**：`ModalManager` 单栈（v0.7.1 的 `activeModal` 泛化为栈，支持确认框叠在面板弹窗上），Esc 关栈顶，背景 `inert`。

## 3. 输入模型（一次性解决 C4 类问题）

单一 keydown 分发器 + 输入上下文栈，取代散落的事件监听：

```
InputContext 栈（高优先级在上）:
  text-entry   聊天框/表单聚焦时 —— 吞掉一切游戏快捷键
  modal        弹层打开时 —— 只响应 Esc / 弹层内快捷键（如对比面板的 E=替换）
  panel        侧栏面板聚焦时 —— 面板内导航键
  global       WASD 移动 / G 采集 / F 战斗 / 1-9 面板切换 / Enter 聚焦聊天
```

- 快捷键以 `{ key, contextScope, action, description }` 注册进 HotkeyRegistry；`description` 直接渲染键位说明面板（v1.0），注册即文档。
- 移动键只存在于 `global` 上下文——任何弹层/输入态天然屏蔽，C4 类 bug 从结构上不可能再发生。
- 验收锚点：新增一个快捷键 = 注册一条记录；`grep addEventListener("keydown")` 全前端只命中分发器一处。

## 4. 客户端状态架构

三层分离，替代 15 个平铺 useState：

1. **服务器状态层（`useGameSync`）**：唯一数据源。所有服务端数据（游戏状态、聊天、在线、日志）经统一同步层进入（见 §5），组件只读订阅，禁止组件私藏服务端数据副本（消灭 `market` 双份状态类问题）。
2. **UI 状态层**：`uiReducer` 管 `{ activePanel, modalStack, drafts(聊天/对话输入), hints }` —— 有限状态、显式迁移。
3. **API 层**：统一 `requestGame` 封装——解析 `ApiErrorBody.error.code` 映射中文文案（复用 AuthPage 已有模式）、401 全局拦截清 session 回登录页、错误分级（toast 级 / 日志级 / 全屏级）。（即审核 I8，实施于此。）

GameShell 拆分目标：shell（布局 + 分发器 + Provider）≤ 200 行；每个面板/弹层独立组件文件；ErrorBoundary 包 shell 与每个面板。

## 5. 状态同步设计（前后端联合，防轮询失控）

问题：按功能各开轮询（进度 3s + 聊天 3s + 在线 15s + 排行 30s），30 客户端 ≈ 每秒 20-40 请求，且每个轮询都可能触发全量状态重算。

方案：**单一同步端点 + 游标增量**。这是 v0.8.0 的前后端联合底盘，不是纯前端工作。

```
GET /game/sync?cursor=<n>
→ {
    cursor: <n'>,
    state?:    GameStateDto,        // 自己的状态有变化才带（版本号比对）
    events[]:  增量事件（日志/掉落/广播）,
    chat[]:    增量聊天（v0.9）,
    presence?: 在线列表（低频，间隔满了才带）,
  }
```

- 游标 = 服务端暴露的单调数字序号，客户端只收增量。
- v0.8.0 明确采用 `sync_events` 投影表，不再把“事件序号 vs 时间戳水位”留到实施阶段。`game_events`/`npc_events` 继续作为展示与审计日志，`sync_events` 是专门给客户端增量同步使用的游标流。
- v0.8.0 payload 最小字段：`cursor`、`serverTime`、`stateVersion`、`state?`、`events[]`。v0.9 才扩展 `chat[]`/`presence?`，但结构预留。
- `stateVersion` = 当前角色可见 `sync_events.id` 的最大值；当 cursor 之后存在 `stateDirty=true` 的事件时返回 `state`，否则只返回事件增量。首次同步（无 cursor）必须返回完整 `state`。
- 客户端单一轮询器：有进行中行动时 3s，空闲 10s，`document.hidden` 时暂停，操作后立即拉一次。
- 服务端 sync 是**纯读**路由（I1 已把任务/传闻生成移入世界 tick 的前提下），可承受高频。
- 未来换 WebSocket：推送同一 payload 结构，客户端订阅层不变——接口即兼容层。
- 性能验收：30 模拟客户端空闲态下服务端 QPS ≤ 5，sync p95 ≤ 100ms。

### 5.1 `sync_events` 最小 schema

```sql
CREATE TABLE sync_events (
  id bigserial PRIMARY KEY,
  account_id uuid,
  character_id uuid,
  audience text NOT NULL CHECK (audience IN ('character','account','public')),
  event_type text NOT NULL,
  state_dirty boolean NOT NULL DEFAULT false,
  source_table text,
  source_id text,
  payload jsonb NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX sync_events_character_cursor_idx ON sync_events(character_id, id);
CREATE INDEX sync_events_public_cursor_idx ON sync_events(audience, id) WHERE audience = 'public';
```

写入规则：
- 任何会改变玩家可见状态的操作，在同一事务内写业务表和 `sync_events(state_dirty=true)`。
- 纯展示事件（掉落 toast、升级横幅、广播高亮）写 `state_dirty=false`，客户端只消费事件不强制刷新完整 state。
- v0.9 聊天/在线/广播可以继续复用同一 cursor 流，不新增独立轮询。

## 6. 反馈层（刷宝游戏的多巴胺管线）

统一由事件流驱动（不是各处 ad-hoc setState）：

- `FeedbackLayer` 订阅 `useGameSync` 的增量事件，按事件类型触发：掉落 toast（稀有度配色，蓝紫加强动效）、升级横幅、全服广播高亮、任务完成提示。
- 稀有度色板全局唯一定义（CSS 变量：白/绿/蓝/紫），事件日志、背包、对比面板、广播复用同一套。
- 错误反馈分三级：字段级（表单内联）、操作级（toast，含具体原因——修复"动作失败请稍后再试"）、会话级（全屏引导回登录）。

## 7. 新手引导框架（v1.0 填内容，v0.8 建骨架）

- 规则驱动提示卡：`{ id, trigger(state/events), content, dismissible }`，如 `first_injury` → 解释受伤机制、`first_loot_rare` → 引导打开对比面板。
- 已读状态存账号（服务端小表或复用 events），换设备不重弹。
- 骨架在 v0.8 随反馈层一起建（成本极低），v1.0 只写触发规则和文案。

## 8. 可用性基线（v1.0 门禁项）

- 长文本：`overflow-wrap: anywhere` 全面板统一（审查 Minor 项在此关闭）。
- 键盘可完成全部核心操作；焦点可见；弹层 focus trap。
- 移动端策略：**明示 PC 优先**——布局在窄屏降级为单栏可浏览（顶栏+主区+底部 tab），保证"能看状态、能聊天"，不承诺完整操作体验；登录页标注建议桌面游玩。
- 色彩对比：稀有度色板与状态色通过 4.5:1 对比检查（暗色底盘尤其注意绿/蓝）。

## 10. 风险与决策

| 项 | 决策/缓解 |
| --- | --- |
| v0.8 同时做物品层+客户端底盘，前后端并行度要求高 | 拆为 v0.8.0 双底盘、v0.8.1 刷宝体验、v0.8.2 内容扩展；客户端底盘 1-3 步不依赖物品层 |
| GameShell 拆分引入回归 | 现有组件测试先行迁移；拆分按面板逐个搬，每步可发布 |
| sync 游标实现选型（事件序号 vs 时间戳水位） | v0.8.0 固定为 `sync_events` 投影表 + bigserial 游标，不使用纯时间戳水位 |
| 聊天增量与全量状态混在一个端点是否过重 | payload 按需附带（state 有版本比对，presence 有间隔门），实测超预算再拆 |
| 不做 WebSocket 是否影响聊天体感 | 3s 轮询对 10-30 人内测足够；payload 结构已按推送兼容设计 |
