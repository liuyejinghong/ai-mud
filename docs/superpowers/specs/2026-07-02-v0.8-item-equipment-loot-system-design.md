# 物品·装备·掉落统一系统设计（v0.8 §4.0/§4.2 执行输入）

状态：设计定稿，待实施
日期：2026-07-02
上游文档：`docs/superpowers/plans/2026-07-02-v0.8-v1.0-closed-beta-roadmap.md`（§4.0/§4.2）、`docs/reviews/2026-07-02-fable5-code-review-report.md`（R2 及引擎专项）
实施前置：v0.7.1 债务修复已合入（本系统会收编其事务模式）

## 1. 目标与问题

### 1.1 要解决的问题（现状证据）

- 装备与道具是两个互不相通的系统：`ItemDefinition.category` 只有 `food | material | ore`，没有 `equipment` 类目；`training_sword` 等新手装备在 `packages/content` 中不存在，是 `game.service.ts` 的 `STARTER_EQUIPMENT` 内联硬编码。
- `character_equipment.itemKey` 是自由文本，属性内联快照，无定义引用，无法追溯、无法批量调参。
- 库存写路径散布在 8 个文件、4 个模块（game/npc-task/dialogue/npc），各自实现"查旧值→算新值→写绝对值"。
- v0.8 要引入词缀装备（唯一实例，非可堆叠），在现有底子上做会把碎片化放大一个数量级。

### 1.2 设计目标

1. 所有"东西"（材料、食物、装备）有唯一的内容定义来源，新增物品只改 `packages/content`。
2. 全仓库只有一个库存/装备写路径（`ItemService`），六个操作原语覆盖全部资产移动场景。
3. 装备实例生成是种子确定性纯函数，可测试、可回放、可批量模拟分布。
4. 每次物品移动留下账本记录（为 v0.10 统一账本预留接口）。

### 1.3 范围边界

- 本版不做：装备上市场交易（唯一实例进市场库存模型复杂，v0.8 用"回收"替代）、NPC 穿戴装备（数据模型预留 `ownerType`，行为推迟）、传奇品质与特效词缀、强化/洗练。
- 玩家↔玩家转移：原语支持（`transfer` 对 owner 无限制），但本版无 UI/路由暴露。
- v0.8.0 必须先建立 Postgres 集成测试底座，再合入资产迁移；迁移/事务/并发类能力不得只靠 mock 单测证明。

## 2. 三层架构

```
packages/content        物品定义注册表 + 词缀池 + 掉落表（纯数据，带校验）
packages/game-rules     item-rules / loot-rules / equipment-rules（纯函数，种子确定性）
apps/server             ItemService（唯一写路径）+ item_instances / item_ledger 表
```

## 3. content 层：统一物品定义注册表

### 3.1 定义 schema（判别联合）

```ts
// packages/content —— 全部物品的唯一定义来源
interface ItemDefinitionBase {
  id: string;              // 稳定 id，全局唯一
  name: string;
  description: string;
  itemLevel: number;
  category: "food" | "material" | "ore" | "equipment";
}

interface ConsumableFields {            // food
  satietyRestore: number;
}

interface EquipmentDefinition extends ItemDefinitionBase {
  category: "equipment";
  slot: "weapon" | "chest" | "head" | "accessory";
  baseStats: { attack?: number; defense?: number; agility?: number; maxHp?: number };
  maxDurability: number;
  affixable: boolean;                   // 新手白装底子也可为 true
}

type ItemDefinition = FoodDefinition | MaterialDefinition | OreDefinition | EquipmentDefinition;
```

### 3.2 类型派生与校验

- `ItemId` 归属定死：**具体物品 id 由 `packages/content` 拥有**，从注册表派生：`export type ItemId = (typeof ITEM_DEFINITIONS)[number]["id"]`。`packages/shared` 不再维护手写 `ITEM_IDS` 业务枚举，也不反向依赖 `packages/content`。
- DTO 边界使用 `string` 承载 `itemId`，在 routes/service 入口通过 content 注册表做运行时校验。这样避免 `shared ↔ content` 循环依赖，也符合“content 定义世界，shared 只定义通信形状”的边界。
- v0.8.0 迁移策略：先把服务端 zod 校验从 `z.enum(ITEM_IDS)` 改为 `z.string().refine(getItemById)` 等运行时校验，再删除或降级 `shared` 中的 `ITEM_IDS`；前端展示始终使用服务端 DTO 下发的 name/category，不在前端依赖 item id 联合类型。
- 内容校验测试（content 包内）：id 唯一；equipment 的 slot/baseStats/maxDurability 合法；词缀引用的 slot 存在；数值范围 min ≤ max；掉落表引用的 itemId 都存在。

### 3.3 词缀池定义

```ts
interface AffixDefinition {
  id: string;                            // 如 "sharp"
  name: string;                          // 如 "锋利"
  stat: "attack" | "defense" | "agility" | "maxHp"
      | "gatherSpeedPct" | "repairDiscountPct" | "durabilityBonusPct" | "injuryRecoveryPct";
  applicableSlots: EquipmentDefinition["slot"][];
  tiers: Array<{ minItemLevel: number; valueMin: number; valueMax: number }>;
}
```

初始词缀池（8 条，数值为内测初始值，全部可调）：

| 词缀 | stat | 适用槽位 | T1（iLvl 1-5） | T2（iLvl 6-10） |
| --- | --- | --- | --- | --- |
| 锋利 | attack | weapon, accessory | +1~2 | +2~4 |
| 坚固 | defense | chest, head | +1~2 | +2~4 |
| 迅捷 | agility | 任意 | +1 | +1~2 |
| 活力 | maxHp | chest, head, accessory | +3~6 | +6~12 |
| 巧手 | gatherSpeedPct | head, accessory | 3~5% | 5~8% |
| 匠心 | repairDiscountPct | accessory | 5~8% | 8~12% |
| 韧性 | durabilityBonusPct | weapon, chest | 10~15% | 15~25% |
| 复元 | injuryRecoveryPct | accessory | 10~15% | 15~20% |

注意：agility 影响 ATB 攻速，是最强属性，数值刻意压低。`gatherSpeedPct`/`repairDiscountPct`/`injuryRecoveryPct` 三条是"生活向"词缀，让非战斗 Build 有存在空间——接入点分别是 `calculateGatheringPlan`、修理报价、受伤时长，实施时在对应规则函数加可选修正参数。

### 3.4 稀有度与掉落表

```ts
type Rarity = "common" | "fine" | "rare" | "epic";   // 白/绿/蓝/紫

interface EquipmentDropEntry {
  kind: "equipment";
  slotPool: EquipmentDefinition["slot"][];   // 从中随机部位
  itemLevelRange: [number, number];
  rarityWeights: Record<Rarity, number>;     // 权重，非概率
  chance: number;                            // 本条目触发率
}
// 怪物 lootTable 扩展为 (原材料条目 | EquipmentDropEntry)[]
```

初始掉落参数（内测初始值）：

| 来源 | 装备掉落率 | 白 | 绿 | 蓝 | 紫 |
| --- | --- | --- | --- | --- | --- |
| 腐林·狼群（T1） | 35% | 55 | 30 | 12 | 3 |
| 旧矿坑·普通怪（T2） | 40% | 45 | 32 | 17 | 6 |
| 旧矿坑·小头目（T2） | 100% | 0 | 55 | 33 | 12 |

词缀条数：白 0、绿 1、蓝 2、紫 2 且数值 roll 结果上浮 25%（向下取整，百分比词缀保留一位小数）。

### 3.5 本版新增 content 清单

- 新手白装迁入定义：`training_sword`（weapon）、`patched_leather_vest`（chest），属性与现有 `STARTER_EQUIPMENT` 一致。
- 新部位白装底子：head、accessory 各 1-2 个定义（T1/T2 各一档）。
- 每槽位 T1/T2 掉落底子：weapon/chest/head/accessory × 2 档 = 8 个装备定义左右（同槽位同档可复用一个底子，稀有度和词缀负责差异化——**底子不需要多，词缀才是差异来源**）。
- 回收价格表（见 §6.4）。

## 4. 规则层：纯函数（`packages/game-rules`）

### 4.1 item-rules.ts（收编 + 新增）

- 收编现有 `addInventoryItem`（堆叠数学）。
- `canEquip(character, definition)`：等级/职业校验（本版仅校验 category === "equipment"，预留扩展）。
- `aggregateEquipmentStats(instances)`：装备实例集合 → 属性总和（攻/防/敏/血 + 生活词缀百分比），替代现有 `equipmentAttackBonus`/`equipmentDefenseBonus` 两个散函数。战斗、采集、修理、受伤四个接入点统一从这里取修正。

### 4.2 loot-rules.ts（新增，全部种子确定性）

```ts
rollLootDrops(seed, lootTable, itemLevelContext): LootDrop[]        // 材料 + 装备条目
rollRarity(seed, weights): Rarity
rollEquipmentInstance(seed, definition, rarity, affixPool): RolledEquipment
// RolledEquipment = { definitionId, rarity, itemLevel,
//                     affixes: Array<{ affixId, stat, value }>,   // roll 时快照数值
//                     maxDurability }                              // 含韧性词缀修正
```

- 种子派生沿用战斗体系：`${combatSeed}:loot:${monsterIndex}:${entryIndex}`、`:affix:${slotIndex}` 等，同一战斗种子回放结果永远一致。
- 词缀选取规则：同一件装备不重复词缀；从 applicableSlots 匹配的池子里按序确定性抽取。
- 复用现有 `chance(seed, index)` 哈希函数，禁止 `Math.random`。

### 4.3 equipment-rules.ts（收编）

现有耐久损耗/修理报价函数收编进来，修理报价接受 `repairDiscountPct` 修正参数。

### 4.4 分布模拟测试（本系统的数值安全网）

规则包内提供 `simulateDropDistribution(seedBase, lootTable, n)`，测试断言 10,000 次掉落的稀有度分布与配置权重偏差 < 2%、词缀数值都在 tier 范围内、无重复词缀。v1.0 调参阶段直接复用这个函数跑参数对比。

## 5. 存储层：schema 变更

### 5.1 `item_instances`（新表，替代 `character_equipment`）

```sql
CREATE TABLE item_instances (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  definition_id text NOT NULL,              -- 引用 content 定义
  owner_type text NOT NULL CHECK (owner_type IN ('character','npc','market','escrow','municipal','system')),
  owner_id uuid NOT NULL,
  location text NOT NULL DEFAULT 'backpack' CHECK (location IN ('backpack','equipped')),
  slot text CHECK (slot IN ('weapon','chest','head','accessory')),
  rarity text NOT NULL DEFAULT 'common' CHECK (rarity IN ('common','fine','rare','epic')),
  item_level integer NOT NULL CHECK (item_level > 0),
  affixes jsonb NOT NULL DEFAULT '[]',      -- [{affixId, stat, value}] roll 时快照，永不重算
  max_durability integer NOT NULL CHECK (max_durability > 0),
  current_durability integer NOT NULL CHECK (current_durability >= 0),
  roll_seed text,                           -- 可审计/回放
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CHECK (current_durability <= max_durability),
  CHECK (
    (location = 'equipped' AND slot IS NOT NULL)
    OR (location = 'backpack' AND slot IS NULL)
  )
);
-- 部分唯一索引：同一角色同一槽位最多一件已装备
CREATE UNIQUE INDEX item_instances_equipped_slot_idx
  ON item_instances(owner_type, owner_id, slot) WHERE location = 'equipped';
CREATE INDEX item_instances_owner_idx ON item_instances(owner_type, owner_id, location);
```

- 实例除耐久外不可变（词缀数值 roll 时快照）；定义调参只影响新掉落。
- owner 模型一次性预留 `character | npc | market | escrow | municipal | system`，避免 v0.10 账本/托管/市政库存再改表结构。v0.8 行为只开放 character/npc/system 必需路径；market/escrow/municipal 作为存储能力预留，不暴露玩家交易。预留 owner 必须有 CHECK 约束和不可达测试，不能变成任意字符串垃圾桶。
- 数据迁移：现有 `character_equipment` 行迁为 `location='equipped'` 的白装实例（definition_id 按 itemKey 映射到 §3.5 迁入的定义）；迁移完成后 `character_equipment` 表下线（保留一版只读，下下版删除）。
- **迁移必须同步 `_journal.json`（教训：C1）。**

### 5.2 `item_ledger`（新表，物品账本）

```sql
CREATE TABLE item_ledger (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  occurred_at timestamptz NOT NULL DEFAULT now(),
  primitive text NOT NULL CHECK (primitive IN ('grant','consume','transfer','equip','unequip','destroy')),
  item_id text,                   -- 可堆叠时非空
  instance_id uuid,               -- 实例时非空
  quantity integer CHECK (quantity IS NULL OR quantity > 0),
  from_owner_type text CHECK (from_owner_type IS NULL OR from_owner_type IN ('character','npc','market','escrow','municipal','system')),
  from_owner_id uuid,
  to_owner_type text CHECK (to_owner_type IS NULL OR to_owner_type IN ('character','npc','market','escrow','municipal','system')),
  to_owner_id uuid,
  reason text NOT NULL,           -- 见 §6.3 reason 枚举
  source_id text,                 -- 关联任务/行动/对话消息 id
  CHECK (
    (item_id IS NOT NULL AND instance_id IS NULL AND quantity IS NOT NULL)
    OR (item_id IS NULL AND instance_id IS NOT NULL)
  )
);
CREATE INDEX item_ledger_owner_time_idx ON item_ledger(to_owner_id, occurred_at);
```

设计意图：v0.10 统一账本（I2）做铜币侧时，`item_ledger` 已就位，两者合并成完整资产账本。

- 可堆叠表 `character_items` / `npc_items` 保持不变（写路径收编即可）。

## 6. 服务层：`ItemService`（唯一写路径）

位置：`apps/server/src/modules/item/`（repository + service + 测试，遵循既有模块模式）。

### 6.1 事务契约

- 所有原语接受 `tx`（Drizzle 事务句柄）作为第一参数，**调用方拥有事务边界**（与 `GameService` 现有模式一致）。
- 可堆叠数量变更一律原子增量 SQL（`SET quantity = quantity + $1`）+ `CHECK (quantity >= 0)` 约束兜底；实例状态迁移一律条件更新 + 检查影响行数（v0.7.1 的模式直接迁移进来）。

### 6.2 六个原语

```ts
interface ItemServicePort {
  // 可堆叠
  grant(tx, { owner, itemId, quantity, reason, sourceId? }): Promise<void>;
  consume(tx, { owner, itemId, quantity, reason, sourceId? }): Promise<void>;    // 不足则抛错
  transfer(tx, { from, to, itemId, quantity, reason, sourceId? }): Promise<void>;
  // 实例
  grantInstance(tx, { owner, rolled: RolledEquipment, reason, sourceId? }): Promise<ItemInstanceRecord>;
  equip(tx, { characterId, instanceId }): Promise<void>;    // 同槽已有装备自动转 backpack（单事务内 unequip+equip）
  unequip(tx, { characterId, instanceId }): Promise<void>;
  destroyInstance(tx, { instanceId, reason, salvage?: { copper } }): Promise<void>;  // 回收在调用方加铜币
}
// owner = { type: "character" | "npc" | "market" | "escrow" | "municipal" | "system", id: string }
```

语义要点：

- `equip` 依据实例的 definition→slot；槽位冲突靠部分唯一索引兜底（并发下第二个 equip 触发约束冲突 → 拒绝）。
- `transfer` = 单事务内 consume(from) + grant(to)，账本记一条 transfer 而非两条。
- 每个原语在同一事务内写 `item_ledger`。
- `destroyInstance` 只删实例记账本；回收铜币由调用方（game.service 回收流程）在同事务内加，未来并入统一钱包服务。

### 6.3 reason 枚举（账本口径）

`starter | loot_drop | gather | eat | market_buy | market_sell | task_deliver | task_reward | dialogue_grant | repair_material | salvage | npc_consume | admin`

### 6.4 装备回收（本版的装备出口）

装备不可上市场。玩家在铁匠处"回收"装备：`destroyInstance(reason: "salvage")` + 铜币 = `itemLevel × 稀有度系数`（白 ×1 / 绿 ×2 / 蓝 ×5 / 紫 ×12，content 常量）。给刷宝一个清包出口和小额铜币来源，同时不冲击市场模型。

### 6.5 调用方收编映射（删除 8 处旧写路径）

| 现有写路径 | 改为 |
| --- | --- |
| `game.repository.setInventoryItem`（采集/吃饭/市场/战利品） | `grant` / `consume` |
| `game.service` 战斗掉落入账 | `grant` + `grantInstance`（装备条目） |
| `game.service` STARTER_EQUIPMENT 发放 | `grantInstance(reason: "starter")` + `equip` |
| `game.service` 修理耗矿 | `consume(reason: "repair_material")` |
| `npc-task.repository.setCharacterInventoryItem/setNpcInventoryItem`（任务交付） | `transfer(reason: "task_deliver")` |
| `dialogue.service` 物资让渡 | `transfer(reason: "dialogue_grant")` |
| `npc.service.addNpcInventoryItem`（NPC 采集/吃饭/抛售/消耗） | `grant` / `consume` / `transfer` |
| `npc.simulation-repository` | 模拟仓库实现同一 Port 的内存版 |

收编完成判定：`grep -rn "update(characterItems\|update(npcItems\|insert(characterItems\|insert(npcItems"` 只命中 `modules/item/`。加一个架构测试固化此断言（读源码文本或 lint 规则均可），防止未来模块绕开。

## 7. DTO 与前端影响

- `EquipmentItemDto` → `ItemInstanceDto`：新增 rarity、affixes（含展示名与数值）、itemLevel、location。
- `GameStateDto.inventory` 拆两段：stackables（现状）+ instances（背包中未装备的装备）。
- 新路由：装备/卸下/回收（走既有 CSRF/session 模式）；掉落进 `gameEvents` 高亮标记。
- 前端：背包装备区、装备对比面板（新旧实例属性并排 diff，含词缀差异）、稀有度配色（白/绿/蓝/紫）。对比面板是刷宝核心 UI，验收以"打开背包中装备 → 与已穿戴同槽位装备并排对比 → 一键替换"为准。
- `apiVersion` bump；`schemaVersion`、`contentVersion`、`rulesetVersion` 按域 bump。

## 8. 测试要求

1. content 校验测试（§3.2）。
2. 规则确定性测试：同种子同输入 → 同 roll 结果；跨进程回放一致。
3. 分布模拟测试（§4.4）：10k 掉落分布偏差 < 2%。
4. 原语并发测试：并发 equip 同槽位（唯一索引拒绝）、并发 consume 超量（CHECK 拒绝）、transfer 原子性（中途失败无半完成态）。
5. 架构测试：写路径唯一性 grep 断言（§6.5）。
6. 迁移测试：空库全迁移 + `character_equipment` 存量数据迁移后属性等值断言（集成测试套件 I5 内）。该套件是 v0.8.0 第一批工作，不是实现后补测。
7. 账本完整性：每个原语调用后 `item_ledger` 有对应记录；一次任务交付/战斗掉落链路的账本可追溯测试。

## 9. 实施顺序（按 v0.8 子版本拆分）

## 10. 风险与开放决策

| 项 | 决策/缓解 |
| --- | --- |
| ItemId 类型派生的包依赖方向（shared vs content） | 已定：content 拥有具体 id，DTO 用 string + 运行时校验，shared 不反向依赖 content（§3.2） |
| 存量开发世界的装备迁移出错 | 迁移测试 + 内测前反正会跑一次世界重置，风险实际很低 |
| 词缀数值失衡 | 分布模拟函数 + v1.0 调参阶段专项；所有数值在 content，调参不动代码 |
| `character_equipment` 下线时机 | 本版保留只读，v0.9 删除 |
| 战斗 payload 中 loot 结构变化（含装备条目） | 与 E2 的 payload 改造（timeline atMs）合并处理，一次迁移 |
| 装备回收价造成铜币注入过量 | 回收计入 item_ledger + 市场税作为对冲；模拟观测货币流速（E6 指标） |
