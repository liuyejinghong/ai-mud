# v0.2 Playable Loop Slice Design

状态：已确认
日期：2026-07-01

## 1. 目标

v0.2 的完整目标是让玩家拥有第一个可玩的 MUD 闭环：创建角色、进入新手村、探索腐林、采集资源、触发自动战斗、受伤回村并获得基础掉落。

本规格只覆盖 v0.2 的第一段，版本建议标记为 `v0.2.0`：

- 角色创建和选择。
- 新手村作为登录后的第一个游戏界面。
- 腐林野外方格地图。
- 键盘 `W/A/S/D` 和鼠标方向按钮移动。
- 基础资源采集。
- 背包中能看到采集所得物品。

自动 ATB 战斗、受伤回村、怪物掉落进入下一段 `v0.2.1`。这样第一段可以快速形成可点、可走、可采集的最小可玩面，同时不把战斗数值和探索状态搅在同一个实现批次里。

## 2. 设计取舍

### 推荐方案：垂直小切片

先实现“角色 -> 村子 -> 腐林 -> 移动 -> 采集 -> 背包反馈”的一条垂直路径。服务端先持久化角色、位置和背包，客户端做 MUD shell。

优点：

- 最快得到可操作体验。
- 后续战斗、经济、NPC 都能复用角色、地图、背包和命令通道。
- 测试边界清楚：不需要先模拟完整世界经济。

缺点：

- 第一段还没有战斗刺激。
- 采集资源的经济价值暂时只进入背包，不进入市场。

### 备选方案：先做战斗规则包

先在 `packages/game-rules` 做 ATB 战斗、怪物和掉落，再接 UI。

优点：规则先行，战斗质量更早可测。

缺点：用户打开游戏仍然看不到可玩的世界入口，反馈周期慢。

### 备选方案：先做世界数据库全量模型

先把地图、角色、背包、物品、资源点、事件和未来战斗全部建表。

优点：后续扩展更从容。

缺点：前期建模容易过度，且还没有实际玩法压力校验字段是否合理。

结论：采用垂直小切片。只建 v0.2.0 必须用到的数据结构，但命名和边界保留 v0.2.1/v0.3 扩展空间。

## 3. 功能范围

### 3.1 角色创建和选择

登录后的玩家如果没有角色，看到角色创建界面。

首批职业：

- 战士：高生命、高护甲，基础采集速度正常。
- 游侠：高敏捷，移动和采集更轻快，后续战斗攻速更快。
- 术士：高智力，首段只展示属性差异，战斗法术留到 v0.2.1。

角色字段：

- `id`
- `accountId`
- `name`
- `classId`
- `level`
- `xp`
- `hp`
- `maxHp`
- `injuryUntil`
- `currentLocation`
- `createdAt`

首段只允许每个账号创建一个角色。多角色槽位后续再加，避免先做角色管理复杂度。

### 3.2 新手村

新手村是安全区，不做探索格子移动。

首段村子只需要：

- 当前地点标题：黑松哨站。
- 简短地点描述。
- 可进入野外入口：腐林。
- 背包摘要。
- 角色属性摘要。

后续 v0.3 会把市政厅、集市、铁匠铺、任务牌接入这里。v0.2.0 不实现交易和 NPC 对话。

### 3.3 腐林地图

腐林是第一张野外探索地图。

首段地图规则：

- 地图大小：`5 x 5`。
- 玩家从南侧入口进入，初始坐标为 `(2, 4)`。
- 地图中有固定出口格，回到新手村。
- 地图中有若干可采集资源点。
- 地图中预留怪物群位置字段，但 v0.2.0 不触发战斗。

移动规则：

- `W`：向北，`y - 1`。
- `S`：向南，`y + 1`。
- `A`：向西，`x - 1`。
- `D`：向东，`x + 1`。
- 不能走出地图边界。
- 每次移动由服务端校验并返回新状态。

客户端可以显示一个简单方格小地图：

- `@` 表示玩家。
- `R` 表示资源。
- `E` 表示出口。
- `?` 表示未探索或普通区域。

地图生成首段采用确定性内容模板，不调用 AI。后续 AI 事件、天气、蘑菇等动态事件在 v0.5 进入。

### 3.4 采集

首段采集是一个即时动作，不做长时间挂机进度条；挂机耗时和中断机制留到 v0.2.1/v0.3。这样可以先验证资源点、背包、命令和 UI。

资源类型：

- `wild_berry`：野莓，食物类。
- `beast_meat`：兽肉，食物/材料类。
- `rough_hide`：粗糙皮革，材料类。

采集规则：

- 玩家站在有资源的格子上才能采集。
- 每个资源点有剩余次数。
- 采集成功后资源进入背包。
- 资源点耗尽后从地图状态中标记为空。
- 每次采集写入服务端日志事件，客户端显示文本反馈。

首段不做：

- 市场出售。
- 饱腹度消耗。
- 资源刷新。
- NPC 抢采。

这些留给 v0.3 经济世界。

## 4. 架构边界

### 4.0 自研 MUD 引擎

本项目不使用 Unity、Unreal、Godot 这类通用图形游戏引擎。它们主要解决渲染、动画、物理、场景编辑器和实时帧循环问题，而本项目首要复杂度在服务端权威状态、文字交互、规则校验、持续世界、AI 约束和资产账本。

本项目需要自研一套服务端权威的 MUD 引擎。它不是一个单独的大型框架，而是一组稳定边界：

用非技术语言说，MUD 引擎的核心目标是：把“很多地图、很多 NPC、很多资源、很多玩法都会反复用到的规则”沉淀成一套可复用底座。以后新增一张地图、一个副本、一类资源、一个 NPC 行为，不应该从零写一遍移动、背包、时间、采集、结算、校验逻辑，而是优先复用已有规则，通过内容配置和少量扩展完成。

这个引擎不是为了炫技，也不是为了第一版做得很大。它的价值只看三件事：

1. 新增内容是否更快。比如新增一张野外地图，主要工作应是写地图、资源、怪物和事件配置，而不是重写底层系统。
2. 已有规则是否能复用。比如野外、村庄、副本、NPC 行程都应该共用同一套位置、时间、背包、物品和日志规则。
3. 未来扩展是否不推倒重来。比如后续加入战斗、经济、AI NPC、任务、市场时，是把新模块接到同一套引擎上，而不是为每个玩法单独搭一套小系统。

如果后续出现“每加一个区域都要写一批专属接口”“同一种移动在不同地图有不同实现”“奖励、背包、时间、日志散落在很多地方各自处理”，就说明 MUD 引擎设计失败，需要回到这一节重新收敛。

- 内容定义层：职业、地图模板、资源、物品、怪物、NPC 和后续副本目标放在 `packages/content`。
- 规则引擎层：移动、采集、背包堆叠、战斗、掉落、饥饿、市场价格等纯规则放在 `packages/game-rules`。
- 世界系统层：时间、天气、资源刷新、NPC 行动循环、后续市场结算等跨地图系统由引擎统一调度。
- 命令处理层：玩家意图进入服务端后，由命令 handler 调用规则引擎并持久化结果。
- 状态持久层：角色、位置、背包、地图实例、日志和后续账本由 `apps/server` 持久化。
- 表现层：`apps/web` 只展示状态和提交意图，不拥有任何权威玩法规则。

引擎目标是让后续新增区域时只需要增加内容和少量规则配置。例如新增一张野外地图，应主要增加：

- 一个地图模板。
- 资源点和怪物群配置。
- 可进入/离开的入口定义。
- 必要的特殊事件规则。

新增区域不能重新实现移动、采集、背包、战斗、奖励结算或权限校验。若新增区域需要改底层规则，应该先扩展 `packages/game-rules` 的通用能力，再让新区域通过配置调用它。

同理，天气、NPC 生成、NPC 日程也不能由每张地图或每个 NPC 自己单独实现：

- 天气应由引擎统一生成和推进。地图可以配置气候倾向，例如寒冷、潮湿、森林、矿区，但不能自己随意决定“昨天暴雪，今天高温”。引擎需要维护季节、区域气候、昨日天气、温度变化范围和特殊天气概率，让天气变化有连续性和逻辑性。
- NPC 应由引擎提供统一生成流程。每个 NPC 的职业、背景、性格、初始资产、生活职业、战斗职业、关系网和日程偏好可以不同，但创建方式不能是手写 50 次或 100 次专属代码。新增 NPC 应主要增加 `NpcDefinition` 和少量配置。
- NPC 日程应由引擎提供统一行动框架。每个 NPC 可以有不同目标，例如采食物、挖矿、打猎、开店、巡逻、休息，但“起床、选择目标、规划路径、移动、执行挂机工作、遇到事件、回村、休息、记忆整理”这些流程应复用同一套调度和行动规则。
- AI 只参与决策和表达，不直接绕过引擎。比如 AI 可以帮 NPC 判断今天下雪不适合采蘑菇，改去打猎；但移动、交易、获得物品、消耗食物、发任务奖励仍必须通过引擎规则和资产账本。

### 4.0.1 MUD 引擎职责总表

长期看，所有后续内容都应该接入 MUD 引擎，而不是单独写一套小系统。引擎负责“世界怎么运转”，内容负责“世界里具体有什么”。这样才能避免地图、NPC、任务、副本各自长出一套重复逻辑，最后变成难维护的代码堆。

引擎应逐步沉淀这些通用能力：

1. 命令系统：键盘、鼠标、文本输入统一转成 `GameCommand`。
2. 地图与位置系统：村庄、野外、副本共用区域、坐标、出口、寻路、可达性规则。
3. 时间系统：现实时间推进游戏时间，并驱动战斗、采集、NPC 行动、天气和市场结算。
4. 天气与环境系统：统一维护季节、气候、天气连续性和环境影响。
5. 角色实体系统：玩家和 NPC 共用位置、属性、背包、装备、状态等基础模型。
6. 物品与背包系统：获得、消耗、堆叠、装备、修理、交易都走统一规则。
7. 账本与资产校验系统：金币、物品、经验、奖励、赠与都有来源、去向和审计记录。
8. NPC 生成系统：NPC 通过定义生成，差异来自职业、背景、性格、资产、关系和偏好。
9. NPC 行动与日程系统：NPC 共用目标选择、路径移动、挂机工作、事件处理、休息和记忆整理流程。
10. 挂机行为系统：战斗、采集、挖矿、打造、修理、疗伤共用开始、推进、结算和中断机制。
11. AI 调用与约束系统：AI 输出只能作为决策或表达提案，必须经过引擎校验才能改变世界。
12. 内容包与扩展系统：地图、副本、资源、怪物、NPC、任务优先通过内容定义接入，只有通用能力不足时才扩展引擎规则。

反向约束：

- 新地图不能自带一套移动系统。
- 新副本不能自带一套奖励结算系统。
- 新 NPC 不能自带一套日程循环。
- 新任务不能自带一套背包扣除和奖励发放逻辑。
- 新 AI 能力不能绕过资产账本、状态机和规则校验。
- 新 UI 不能拥有服务端权威规则，只能展示状态和提交意图。
- 新内容如果需要复制大量旧代码，说明应该先抽成引擎能力，再接内容。

v0.2.0 的第一版 MUD 引擎只包含四个最小能力：

- `GameCommand`：统一表达创建角色、进入区域、移动、采集、回村等玩家意图。
- `GameState`：统一返回角色、当前位置、地图、背包、日志和可执行动作。
- `MapRules`：处理方格地图边界、坐标移动、出口和资源点判断。
- `InventoryRules`：处理物品堆叠和数量变化。

v0.2.1 再把 `CombatRules` 接入同一套命令和状态模型。v0.3 再把 `EconomyRules`、`LedgerRules` 接入。后续天气、NPC、任务、AI、副本也按职责总表逐步接入。这样扩展不是重新搭建底层，而是在同一套 MUD 引擎上持续增加模块。

### 4.0.2 MUD 引擎调研结论

调研对象：

- Evennia：现代 Python MUD/MU* 框架，强调 persistent typeclasses、commands、scripts、ticker handler。参考：<https://www.evennia.com/docs/latest/Components/Typeclasses.html>、<https://www.evennia.com/docs/latest/Components/Commands.html>、<https://www.evennia.com/docs/latest/Components/Scripts.html>、<https://www.evennia.com/docs/latest/Components/TickerHandler.html>。
- Ranvier：Node.js MUD 引擎，强调 bundle、area、entity loader、command、script/behavior。参考：<https://ranviermud.com/>、<https://ranviermud.com/bundles/>、<https://ranviermud.com/building/>、<https://ranviermud.com/building/scripting/>。
- CircleMUD / DikuMUD 系：经典 room/zone/mobile/object 文件和 reset 思路。参考：<https://www.circlemud.org/cdp/building/building-3.html>、<https://www.circlemud.org/cdp/building/building-4.html>、<https://www.circlemud.org/cdp/building/building-5.html>。
- CoffeeMUD：成熟 Java MUD 引擎，包含 locale、room、area、tick、reset、admin/building 工具。参考：<https://coffeemud.org/>、<https://www.coffeemud.net/guides/ArchonGuide.html>。
- LPMud / MOO：强调 driver/mudlib 或 object/verb/property 的可扩展世界模型。参考：<https://en.wikipedia.org/wiki/LPMud>、<https://en.wikipedia.org/wiki/MOO>。

可采纳原则：

1. 引擎和内容必须分层。LPMud 的 driver/mudlib 分离、Ranvier 的 core/bundle 分离都说明：底层引擎要尽量少带具体游戏世界偏见，具体地图、物品、NPC、任务通过内容包和脚本扩展。
2. 内容实体必须有稳定 ID。CircleMUD 的 virtual number、Ranvier 的 `area:id` entity reference 都说明：房间、资源、怪物、物品不能只靠显示名定位。我们的内容 ID 使用 `zoneId:entityId` 风格，例如 `corrupt_forest:wild_berry_patch_01`。
3. 区域坐标应是局部坐标。Ranvier 的 area-local coordinates 适合我们：腐林的 `(2, 4)` 只在 `corrupt_forest` 内有效，未来旧矿道也可以有自己的 `(2, 4)`，两者互不冲突。
4. 命令要和输入方式解耦。Evennia/Ranvier 都把玩家输入归一到 command。我们的键盘、鼠标、未来文本命令都必须转成同一类 `GameCommand`，不能让 `W` 键单独走一套移动逻辑。
5. 时间系统不要依赖一个全局大 tick。Evennia 的 ticker handler 采用订阅模型；CoffeeMUD 有世界时间和 tick 管理工具。我们的 `WorldClock` 应支持按系统订阅：玩家战斗、NPC 日程、资源刷新、市场结算可以是不同 tick，不要所有对象每秒一起跑。
6. 脚本/行为要可组合，但不能越权。Ranvier 把 entity script 和 behavior 分开，CoffeeMUD 有 behaviors/properties。我们后续可以有 `BehaviorRules`，但行为只能提出动作或调用规则，不能直接改资产。
7. 管理工具是引擎的一部分。CoffeeMUD 的 reset、export/import、list ticks、time advance 等管理能力说明，持续世界必须可观察、可回滚、可重置。v0.2.0 不实现完整 GM 工具，但所有状态变化必须有清晰日志，为 v0.6 管理后台留接口。
8. 可扩展属性要克制。Evennia Attributes/MOO properties 证明动态属性很灵活，但也容易失控。我们首版只允许内容定义中的 `metadata` 保存表现层扩展；影响规则的字段必须进入 typed schema 或 typed content definition。

因此，本项目的 MUD 引擎采用“typed core + content packs + command handlers + scheduled systems”的结构：

```text
Client Input
  -> GameCommand
  -> Command Handler
  -> GameRules
  -> Repository Transaction
  -> GameState + GameEventLog
```

新区域开发流程必须是：

1. 在 `packages/content` 新增 `ZoneDefinition`。
2. 使用通用 `MapRules` 表达坐标、出口、资源点和危险格。
3. 如需特殊行为，先写可复用 `BehaviorRule`，再在区域内容里配置。
4. 服务端 route 只调用通用 command handler，不为单个区域写专属移动/采集 route。
5. UI 只按 `GameState` 渲染，不为单个区域硬编码规则。

### 4.0.3 MUD 引擎版本策略

MUD 引擎本身会迭代，因此除了主路线图里的 `ruleset_version`，v0.2 起在文档和代码中区分三类版本：

- `engine_version`：命令协议、状态模型、调度模型、引擎边界变化。
- `ruleset_version`：移动、采集、战斗、经济等规则公式变化。
- `content_version`：职业、地图、资源、怪物、物品、NPC 定义变化。

首段实现可以先把 `engineVersion` 暴露在共享常量和 release note 中；数据库 `world_version` 表可在后续 schema 任务中统一补齐。任何破坏 `GameCommand` 或 `GameState` 兼容性的修改，都必须提升 `engine_version`，并在 release note 写明迁移影响。

### 4.1 服务端权威

客户端只提交意图：

- `createCharacter`
- `enterZone`
- `move`
- `gather`
- `returnToVillage`

服务端负责：

- 校验账号 session。
- 找到当前角色。
- 校验移动边界。
- 校验资源点存在。
- 更新角色位置和背包。
- 返回新的游戏状态。

### 4.2 包边界

`packages/content`：

- 职业定义。
- 腐林地图模板。
- 资源定义。

`packages/game-rules`：

- 移动边界校验。
- 采集结果计算。
- 背包堆叠规则。

`packages/shared`：

- 角色 DTO。
- 地图 DTO。
- 背包 DTO。
- 游戏命令/响应 DTO。

`apps/server`：

- 数据库 schema。
- 角色、世界状态、背包 repository。
- HTTP routes。

`apps/web`：

- 游戏 shell。
- 角色创建页。
- 地点视图。
- 方格地图。
- 快捷键和鼠标方向按钮。
- 背包/日志展示。

## 5. 数据模型

首段需要新增持久化表：

- `characters`
- `character_inventories`
- `character_world_states`

设计原则：

- 账户和角色分离。
- 背包用 `item_id + quantity` 堆叠。
- 当前地图状态先存为 JSON，便于快速迭代腐林资源点；后续如果资源/NPC/事件复杂，再拆成规范表。

建议：

- `characters.current_location` 存 `village:black_pine` 或 `zone:corrupt_forest`。
- `character_world_states.zone_state_json` 存腐林坐标、已探索格、资源点剩余次数。
- `character_inventories.item_id` 使用 content 稳定 ID。

## 6. UI 和交互

首段 UI 不做营销页，登录后直接进入游戏 shell。

游戏 shell 布局：

- 左侧：角色状态和背包摘要。
- 中间：地点描述、事件日志、主要操作。
- 右侧：小地图和方向按钮。
- 底部：输入栏预留，但首段不实现复杂文本命令。

键盘：

- 在腐林中监听 `W/A/S/D`。
- 在输入框聚焦时不触发移动。
- 鼠标方向按钮和键盘使用同一条命令路径。

移动反馈：

- 成功：日志显示“你向北移动，树影遮住了回路。”
- 失败：日志显示“边界被倒伏的黑木挡住。”
- 资源格：日志提示“这里有可采集的野莓。”

## 7. 错误处理

- 未登录：返回 `UNAUTHENTICATED`。
- 没有角色：返回需要创建角色的状态。
- 非法职业：返回 `VALIDATION_ERROR`。
- 移动越界：返回 `VALIDATION_ERROR`，不改变位置。
- 不在野外地图：移动或采集返回 `VALIDATION_ERROR`。
- 没有资源：采集返回 `VALIDATION_ERROR`。

所有资产变化必须服务端计算。客户端不能直接改背包。

## 8. 测试和验收

必须覆盖：

- 职业内容定义存在且稳定。
- 移动规则阻止越界。
- 采集会减少资源点次数并增加背包数量。
- 未登录不能访问游戏状态。
- 已登录但无角色会看到创建角色入口。
- 创建角色后进入新手村。
- 进入腐林后可以用键盘或鼠标移动。
- 站在资源点可以采集并看到背包数量变化。

验收：

- 新账号注册登录后，3 分钟内能创建角色并进入新手村。
- 玩家能进入腐林并移动至少 3 格。
- 玩家能采集至少一种资源。
- 背包显示采集所得。
- 刷新页面后角色和背包状态仍在。

## 9. 不做范围

v0.2.0 不做：

- 自动 ATB 战斗。
- 受伤回村。
- 怪物掉落。
- 饥饿。
- 市场经济。
- NPC 日程。
- NPC AI 对话。
- AI 地图生成。
- 副本。
- WebSocket 实时推送。

这些都保留在既定路线图中，不能在 v0.2.0 实现时顺手扩张。

占位符扫描：未发现占位文本或未定义行为。

一致性检查：本规格与主路线图一致，把 v0.2 Playable Loop 拆成 `v0.2.0` 和 `v0.2.1`；第一段不包含战斗，第二段接自动 ATB。MUD 引擎边界明确为内容定义、规则引擎、命令处理、状态持久和表现层五部分。
