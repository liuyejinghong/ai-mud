# v0.10.6C 玩家闭环执行计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 确保新玩家和返回玩家始终拥有合法下一步，在对话中完成 NPC 任务，并在不丢失上下文的情况下获得错误、时间和地点反馈。

**架构：** 把 `availableActions` 视为权威能力契约。增加一条有界且可审计的恢复路径；在任务所属 NPC 处提供交互；纯 UI 表达修复不侵入规则所有权。

**技术栈：** TypeScript、Fastify、PostgreSQL/Drizzle、共享 DTO、React、Vitest、Playwright fixtures。

### 任务 2：持久化救济冷却并增加动作

- [ ] **Step 1: Add shared contracts**

Add `claim_relief` to the action union and a mutation response through the existing GameState DTO. No client-provided item or quantity is accepted.

- [ ] **Step 2: Create the next migration**

Add `last_relief_claimed_at` to `characters`. Register the migration, mirror schema, bump `schemaVersion`, `apiVersion`, and `rulesetVersion` as required.

- [ ] **Step 3: Write service tests**

Cover:

- eligible market-stock relief;
- ineligible cooldown;
- ineligible when player owns food;
- concurrent duplicate claim, where only one conditional timestamp update succeeds;
- emergency source when market lacks food;
- ledger/event/audit records.

- [ ] **Step 4: Implement atomic claim ownership**

First claim the cooldown with a conditional update:

```text
UPDATE characters
SET last_relief_claimed_at = now
WHERE id = characterId
  AND (last_relief_claimed_at IS NULL OR last_relief_claimed_at <= now - 24h)
```

If 0 rows update, reject. Then lock market food inventory and decrement one if stock exists above reserve. Otherwise issue one emergency `wild_berry` through ItemService and record a system-source ledger entry. Every step remains in one transaction.

### 任务 7：增加真实玩家闭环 E2E 基础设施

- [ ] **Step 1: Separate mock smoke and real E2E projects**

Keep mock component smoke tests, but add a Playwright project named `real-postgres` that starts a dedicated server with a temporary database and runs migrations before the suite.

- [ ] **Step 2: Add deterministic test setup**

The setup script must:

```text
create temporary database → run migrations → seed admin and one activation code
→ expose activation code to Playwright through process environment
→ drop temporary database after tests
```

Never use the developer's normal database.

- [ ] **Step 3: Implement the real flow**

The real browser test performs actual UI operations without `page.route()`:

```text
register → login → create character → enter corrupt forest → move to resource
→ start test-cycle gathering → wait for server settlement → verify backpack and event stream
→ send lobby chat → logout → login again → verify the same character and inventory persist
```

Use a test-only gathering-cycle configuration injected through the server environment, and reject
that setting outside `NODE_ENV=test`. Do not make browser time, a test-only HTTP endpoint, or a
database mutation the source of truth for action settlement.

This test is deliberately a cross-layer smoke test, not a one-file regression suite for every
feature. Combat timing/drop variance, equipment details, market and NPC-task escrow, and their
concurrency guarantees stay in their focused rule/service/PostgreSQL tests. A failure here should
identify a broken real player seam, rather than leave an ambiguous 90-second scenario to diagnose.
The logout step is part of the product contract: a signed-in player needs an explicit way to end a
session before persistence can be truthfully re-verified.

- [ ] **Step 4: Repair stale mock E2E assertions**

Update equipment tests to open the detail modal and admin tests to use the final AdminShell from Package D. Do not delete assertions merely to turn the suite green.

- [ ] **Step 5: Run and commit**
