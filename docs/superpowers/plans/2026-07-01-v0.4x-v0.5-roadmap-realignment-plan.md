# v0.4.x / v0.5 Roadmap Realignment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Re-align the next development steps so economy completion work stays in `v0.4.x`, and `v0.5.0` remains reserved for Living NPC.

**Architecture:** Treat the release roadmap as the source of truth. `v0.4.x` owns deterministic economy sinks, needs, ledgers, repair, wages, and market foundations; `v0.5.x` owns long-term NPC residents that reuse those deterministic systems; `v0.6.x` owns AI dialogue, AI task proposal, and memory compression on top of real world state.

**Tech Stack:** TypeScript monorepo, Fastify server, React/Vite web client, PostgreSQL/Drizzle persistence, shared typed contracts, `packages/game-rules`, `packages/content`, Vitest, Playwright.

---

## 1. Why This Document Exists

After `v0.4.0` shipped, the next suggested work was described as `v0.5: equipment durability and repair loop`. That label was wrong.

The work itself is valid, but it belongs to the existing `v0.4.x Economy World` track, not to `v0.5.x Living NPC`.

This document fixes the planning boundary before more code is written.

## 2. Original Roadmap Truth

The master roadmap defines:

- `v0.4.x` Economy World: hunger, market, ledger, resources, taxes, repair, wages.
- `v0.5.x` Living NPC: long-term NPC movement, jobs, schedules, memory summaries.
- `v0.6.x` AI Layer: NPC dialogue, AI tasks, prompt safety, memory compression.

Therefore:

- Equipment durability is `v0.4.x`.
- Repair execution is `v0.4.x`.
- Hunger and food consumption are `v0.4.x`.
- NPC wallets, inventories, location, work, schedules, movement, and memory summaries are `v0.5.x`.
- AI dialogue and AI-generated tasks are `v0.6.x`.

## 3. Current Implementation Truth After v0.4.0

`v0.4.0` delivered the economy foundation, not the entire Economy World.

Completed:

- Copper-backed money model with gold, silver, copper display.
- Municipal market entry in the village.
- Market inventory, buy price, sell price, tax, and stock-sensitive pricing.
- Market buy/sell routes.
- Market transaction persistence.
- Basic iron ore item and resource point.
- Repair quote rule skeleton using copper plus iron ore.
- Frontend market modal.
- Playwright coverage for entering the market UI.

Not completed:

- Hunger meter.
- Food consumption and auto-eat.
- Equipment durability.
- Repair execution that changes durability and consumes materials.
- Ledger query UI/API for operators or players.
- NPC wages.
- NPC autonomous buying/selling.
- 3-day no-player economy simulation.

## 4. Correct Placement Of The Previously Suggested Work

The previously suggested "equipment durability and repair loop" should be renamed and placed as:

```text
v0.4.1 Economy Sink: Equipment Durability And Repair Execution
```

It is not `v0.5.0`.

Reason:

- Iron ore was added in `v0.4.0` specifically to avoid fake money-only repair.
- Repair quote rules already exist, but the player cannot yet complete a real repair.
- Durability is an economic sink: it consumes money and materials.
- Living NPC should later reuse this system for blacksmith behavior, miner demand, and equipment upkeep.

## 5. Proposed v0.4.x Split

The original `v0.4 Economy World` scope is too large for one clean release. Keep it as a version family and split it into smaller internal releases.

### v0.4.1 Economy Sink: Equipment Durability And Repair Execution

Goal: Complete the repair loop that `v0.4.0` prepared.

Included:

- Equipment instances gain current durability and maximum durability.
- Combat and gathering can reduce durability through deterministic rules.
- Repair quote uses actual durability loss instead of a placeholder loss ratio.
- Repair execution consumes copper and basic iron ore.
- Repair restores durability.
- Repair writes a ledger or transaction record.
- UI shows equipment durability and a repair action when repair is possible.

Acceptance:

- A damaged item cannot be repaired for free.
- Repair fails if the player lacks copper.
- Repair fails if the player lacks basic iron ore.
- Repair succeeds by consuming both copper and basic iron ore.
- Repair result is persisted and visible after refreshing game state.
- Tests prove repair cost is rule-driven, not hardcoded in the frontend.

### v0.4.2 Basic Needs: Hunger And Food Consumption

Goal: Make food a recurring economic demand for players first.

Included:

- Character hunger or satiety meter.
- Scheduled meal-time hunger reduction through server-side settlement.
- Manual eat action.
- Auto-eat from lowest item-level food first.
- Low hunger penalties.
- Zero hunger injury return or forced village recovery.
- Market food price remains affected by stock.

Acceptance:

- Food shortage matters because food is consumed over time.
- The player gets clear warnings before severe hunger penalties.
- Auto-eat never consumes premium food before ordinary food when ordinary food exists.
- Hunger settlement is server-authoritative.

### v0.4.3 Economy Visibility: Ledger Query And Municipal Controls

Goal: Make the economy diagnosable before NPCs start participating in it.

Included:

- Ledger query API.
- Market inventory admin/read-only panel.
- Tax totals.
- Municipal stock movement visibility.
- Soft balancing values for food, ore, taxes, and repair coefficients.

Acceptance:

- Operators can inspect market transactions without reading the database directly.
- Tax and stock changes can be traced to player actions.
- Economic bugs can be diagnosed before adding autonomous NPC traffic.

### v0.4.4 Cancelled As A Standalone Release

The previously proposed `v0.4.4 Wage And Simulation Skeleton` should not ship as a standalone gameplay release.

Reason:

- A real economy cannot run without producers and consumers.
- If there is no NPC movement, gathering, buying, selling, eating, or repair behavior, a "no-player economy simulation" can only be a static scenario test or fake aggregate model.
- The project explicitly rejects fake background NPC tiers. Therefore simulation must be driven by real long-term NPC records using the same economy, action, hunger, inventory, and market systems as players.

The useful parts of the old `v0.4.4` scope move into `v0.5.0`:

- Wage policy.
- Municipal budget or controlled wage source.
- Multi-day simulation report.
- Economy deadlock checks.

These are validation and support systems for Living NPC, not a separate release before NPCs exist.

## 6. Correct v0.5.0 Boundary

`v0.5.0` should start now that the deterministic player economy foundation exists.

The release must include the minimum real NPC behavior required for the economy to move. It should not simulate an economy with abstract background actors.

`v0.5.0 Living NPC` should include:

- Six long-term NPCs: farmer, hunter, miner, blacksmith, merchant, municipal officer.
- NPC wallet, inventory, hunger, equipment, home, and current location.
- Daily plan structure.
- Grid movement without teleporting.
- Gathering, mining, hunting work activities using the same active-action engine as players.
- NPC buying and selling through the same market rules as players.
- Wage policy and controlled municipal wage source.
- Food consumption and auto-eat using the same hunger rules as players.
- Multi-day no-player simulation driven by those real NPC records.
- NPC injury handling.
- Nightly memory compression stub without external AI calls.
- NPC admin detail view.
- 7-day simulation with no world deadlock.

`v0.5.0` should not include:

- Free-form AI dialogue.
- AI-generated quests.
- AI reward decisions.
- AI memory compression using a real model.
- Dungeon AI generation.

Those belong to `v0.6.x` or later.

## 7. Correct v0.6.0 Boundary

`v0.6.0 AI Layer` should be built after deterministic NPC life exists.

Included:

- AI provider adapter.
- Structured AI calls with output schemas and length limits.
- Roleplay NPC dialogue.
- AI task proposal from real NPC needs and real NPC inventory.
- Memory summarization and compression.
- Prompt-injection fixtures.
- Template fallback when AI fails.

Authority boundary:

- AI may propose intent, dialogue, tasks, and memory summaries.
- AI may not directly mint items, money, experience, stats, or combat results.
- Rewards must come from system-backed fixed tasks, dungeon rewards, or real NPC inventory/wallet.

## 8. Immediate Recommendation

The next implementation should be:

```text
v0.4.1 Economy Sink: Equipment Durability And Repair Execution
```

This is recommended because `v0.4.0` already created the market, money, iron ore, and repair quote skeleton. Completing durability and repair turns iron ore from a display resource into a real economic sink.

After that, continue with:

```text
v0.4.2 Basic Needs: Hunger And Food Consumption
v0.4.3 Economy Visibility: Ledger Query And Municipal Controls
v0.5.0 Living NPC
v0.6.0 AI Layer
```

## 9. Guardrails For Future Planning

- Do not rename deterministic economy work as `v0.5`.
- Do not start Living NPC until NPCs can reuse existing market, inventory, action, hunger, and repair concepts.
- Do not start AI tasks until deterministic NPC needs and inventories exist.
- Do not let AI create rewards from nothing.
- Do not implement one-off NPC logic outside the MUD engine and shared rule packages.
- Every release note must state both completed work and explicitly excluded work.
