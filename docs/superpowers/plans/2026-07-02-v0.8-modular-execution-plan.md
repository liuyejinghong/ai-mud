## 1. 目标

v0.8 的目标不是“堆更多功能”，而是建立内测核心体验的两块底盘，并在其上跑通第一条刷宝闭环：

1. **资产底盘**：所有物品、装备、掉落、库存写入都走统一内容定义、规则函数、`ItemService`。
2. **客户端底盘**：HUD、输入、弹层、同步、反馈层有统一框架，后续大厅/聊天/报告不继续堆进 GameShell。
3. **刷宝闭环**：新玩家能升级、掉装备、比较装备、替换装备，并感受到掉落反馈。
4. **内容可复用**：旧矿坑作为第二张图验证 zone/content 驱动，不允许再为每张地图写一套专用逻辑。

## 2. 拆分原则

- 按模块边界拆，不按“谁顺手改哪个文件”拆。
- 每个模块有明确产物、依赖、验收证据；没有验收证据不算完成。
- v0.8.0 只打地基，不追求完整刷宝体验；v0.8.1 才做第一条体验闭环；v0.8.2 再扩内容。
- v0.8.0 有硬范围刹车：只做 v0.8.1 刷宝闭环必需的底盘。若双底盘超过 2 周，优先保 Postgres 集成测试、ItemService、`/game/sync` 和输入守卫；Panel Registry 深化、ErrorBoundary 细分、开发态事件过滤可顺延，不得用底盘工程继续挤压刷宝验证。
- AI 不获得新权限。v0.8 的资产、掉落、装备、成长全部由规则/内容/服务层决定。
- 所有新增持久化和资产变动继续沿用 v0.7.1 的事务、条件更新、原子增量、防并发模式。

## 4. 功能模块与分工

### A. 测试与迁移底座

责任类型：测试/基础设施。

范围：
- 建立 Postgres 集成测试套件：空库迁移、种子、冒烟链路、资产/铜币基础断言。
- 所有新增迁移必须进入该套件。
- 迁移 journal/schema/version 继续作为发布门禁。

依赖：v0.7.1 迁移验证脚本和事务修复经验。

验收：
- 空库全迁移可重复跑。
- 后续 B/C/D 模块的数据库变更都能被集成测试覆盖。
- CI 中至少有一条真实 Postgres 链路，不再只靠 mock。

落点：v0.8.0 第一批。

### B. 资产与装备底盘

责任类型：后端资产/规则工程。

范围：
- `packages/content`：统一 `ItemDefinition`、equipment 类目、词缀池、掉落表、新手装备迁移。
- `packages/game-rules`：item-rules、loot-rules、equipment-rules，掉落/词缀种子确定性。
- `apps/server`：`ItemService`、`item_instances`、`item_ledger`、写路径收编。
- 为 I3 收编资产写路径；市场库存原子递减作为遗留路径继续跟进。
- `ItemId` 边界：content 拥有具体 id，shared DTO 使用 string，routes/service 通过 content 注册表运行时校验；不得让 shared 反向依赖 content。

不做：
- 玩家间交易。
- 装备上市场交易。
- NPC 自动穿戴装备。
- 传奇/特效词缀/强化洗练。

验收：
- 新增一种装备只改 content。
- 全仓库库存/装备写路径只剩 `ItemService`。
- 同一战斗种子掉落结果可回放。
- 并发 consume/equip/transfer 有失败路径测试。

落点：v0.8.0 建底盘，v0.8.1 接玩法。

### C. 客户端 HUD 与同步底盘

责任类型：前端交互/同步工程。

范围：
- 输入上下文栈、HotkeyRegistry、ModalManager。
- API 层统一错误码/401 拦截，关闭 I8。
- `/game/sync` v1：`sync_events` 投影表 + bigserial 游标、单轮询器、state/events 增量。
- GameShell 拆分、Panel Registry、ErrorBoundary 骨架。
- 为 I1 建立纯读 sync 主路径；旧动作/state 路由中的任务/传闻同步继续跟进。

不做：
- WebSocket。
- 完整移动端体验。
- 大厅聊天/在线列表（v0.9 接入）。

验收：
- 前端 `keydown` 监听只剩统一分发器。
- 任意弹层/输入态不会触发移动键。
- 有行动时进度自动刷新，空闲态 30 客户端 QPS 达标。
- `/game/sync` 不触发世界写入。
- `sync_events` 由业务事务写入，sync 路由只读该游标流；不得用 createdAt 时间戳拼增量。

落点：v0.8.0。

### D. 刷宝玩法垂直切片

责任类型：玩法集成/前后端联合。

范围：
- XP 曲线、等级成长、职业成长数据。
- 战斗掉落接入装备实例。
- 背包/装备面板、装备对比弹层、一键替换。
- 掉落 toast、升级横幅、事件日志高亮、稀有度色板。
- 新手 30 分钟体验验收。

依赖：
- B 的 `ItemService` 和掉落规则。
- C 的同步/反馈层。

验收：
- 新角色 30 分钟内能升 2 级、掉 1 件绿装以上并完成一次装备替换。
- 装备对比能看出旧/新属性、词缀、耐久差异。
- 掉落/升级反馈来自统一事件流，不是组件局部状态。

落点：v0.8.1。

### E. 内容与地图扩展

责任类型：内容/引擎工程。

范围：
- 旧矿坑 zone：T2 怪物、铜矿/铁矿资源点、小头目、T2 掉落。
- `enterZone(zoneId)` 与 zone 注册表，删除新增地图时的专用入口倾向。
- 遭遇冷却，堵住无限刷。
- 第三张测试 zone 作为内容驱动验收样例。

不做：
- 共享野外地图。
- 副本地图。
- 天气随机事件扩展。

验收：
- 加第三张测试 zone 只改 content 不改 service。
- 旧矿坑能进入、能战斗、能掉落 T2 装备。
- 遭遇胜利后进入冷却，逃跑/失败不产生无成本刷怪路径。

落点：v0.8.2。

### F. 模拟、发布与回归

责任类型：验证/发布工程。

范围：
- 7 天模拟回归：NPC 空闲率、资源存量、任务触发、货币流速、掉落分布。
- 发布说明：中文，列出版本常量、迁移、验证证据、已知风险。
- 审核项关闭表：I1/I3/I5/I8 在 v0.8 发布说明中逐项说明。

验收：
- `pnpm -r test/typecheck/lint/build` 全绿。
- `git diff --check` 通过。
- 7 天模拟经济活性不劣化。
- 发布说明能回答“这个版本改了什么、怎么证明没破坏世界”。

落点：每个子版本都要做，v0.8.2 做总回归。

## 5. 并行与依赖关系

可以并行：
- A 测试底座、B content/rules 初稿、C 前端输入/API 层可以并行。
- B 的纯规则测试与 C 的 Modal/Input 不互相阻塞。

必须串行：
- B 的 schema 迁移合入前，A 的 Postgres 集成测试底座必须先可用。
- D 刷宝体验必须等 B 的 `ItemService` 最小可用和 C 的反馈层接口稳定。
- E 旧矿坑必须等 zone 注册表方案落地；否则会回到专用地图代码。

集成点：
- B → C：`GameStateDto`、`ItemInstanceDto`、掉落/装备事件结构。
- C → D：FeedbackLayer 和 Panel Registry。
- D → E：掉落表、区域门槛、旧矿坑装备等级。
- F 横切所有模块：每个子版本都要收验证证据。

## 8. 需要避免的跑偏

- 不要在 v0.8 做副本、共享野图、玩家交易、WebSocket。
- 不要为了装备系统把 NPC 穿戴装备一并做完；数据预留即可。
- 不要让 AI 参与掉落、奖励、属性、库存判定。
- 不要把 `/game/sync` 做成“顺手结算世界”的接口；世界结算只能走 tick/runtime。
- 不要再向 GameShell 增加常驻区和散装状态；新功能默认注册到面板或弹层。
