## 1. 版本目标

v0.9 只解决两个产品体感：

1. **我和朋友在同一个世界里玩。**
2. **这个世界记得我离开后发生了什么。**

因此本版的核心不是扩内容，而是把 v0.8 已经建立的 `sync_events`、`/game/sync`、Panel Registry、FeedbackLayer、AI 边界策略继续往前接线。正确的 v0.9 应该让玩家看到彼此、看到世界广播、看到离线期间的世界摘要；不应该在这个阶段引入玩家交易、共享野外、WebSocket 或新副本。

## 2. 自审结论

### 2.1 逻辑成立的部分

- 大厅聊天、在线状态、排行榜、稀有掉落广播都属于“同服体感”，可以共用 `/game/sync` 的增量模型，不需要各自开轮询。
- 离线世界报告是当前最高性价比的 AI 功能：规则层选真实事件，AI 只把事实改写成更有氛围的摘要，符合“AI 不掌权”的边界。
- NPC 记忆连续性只做表达层增强，不扩展 NPC 的资产/任务/奖励权限，风险可控。
- v0.9 可以继续复用 v0.8 的 HUD 底盘，新增内容默认进侧栏面板，不继续膨胀 GameShell。

### 2.2 必须防止跑偏的部分

- 不做 WebSocket。10-30 人内测阶段单轮询足够，先证明 payload 和游标模型稳定。
- 不做玩家交易。交易会牵涉账本、税、通胀、防刷和纠纷，必须等 v0.10 守恒/运营工具完成后再进入。
- 不做共享野外同屏。共享野外会触发双轨行动统一、事件归属、抢怪/抢资源等问题，不是 v0.9 的必要条件。
- 不新增 AI 权限。`offline_summary` 只能总结事实，不能承诺奖励、发任务、改好感、改变库存或写经济状态。
- 不在 `/game/sync` 里推进世界。同步端点必须保持纯读，世界变化继续走 tick/runtime 或业务事务写入。

## 3. 架构边界

### 3.1 服务端

- repository：只封装 Drizzle 查询与条件更新。
- service：构造注入、框架无关，处理业务规则、事务、同步事件写入。
- routes：只做鉴权、zod 校验和 DTO 输出。
- 公开事件、聊天、在线、排行榜都通过明确服务进入 `/game/sync`，不得在路由里散装查表拼 payload。
- 聊天写入、广播写入、角色状态变化必须在同一事务内写业务表和 `sync_events`。

### 3.2 前端

- 大厅、报告、排行榜都作为 Panel Registry 面板挂载。
- 聊天输入使用 `text-entry` 输入上下文，结构性屏蔽移动快捷键。
- 掉落广播、系统公告、世界传闻统一进入事件日志/反馈层，不新增常驻区。
- 全局只保留一个同步轮询器；新增面板只能订阅同步层数据，不允许自己开定时请求。

### 3.3 AI

- 新增 purpose：`offline_summary`。
- 必须配套：policy、模板 fallback、审计日志、token 上限、边界测试。
- 输入只能是规则层筛选出的事实列表；输出只能是短摘要文本。
- 失败、超时、预算超限、AI 关闭时都返回模板摘要。

## 4. 版本拆包

推荐拆成 4 个独立开发包，按顺序执行。前两个包建立同服底座，第三个包把刷宝反馈接入多人，第四个包再接 AI 放大器。

### v0.9.0 同步与大厅数据底座

目标：让服务端具备“多人可见”的最小数据能力，但前端只做最小验证入口。

范围：
- 新增聊天消息表。
- 新增在线状态模型：基于 session heartbeat 或 `last_seen`，不做复杂 presence 服务。
- 新增排行榜查询：等级榜、财富榜。
- 扩展 `/game/sync` payload：`chat[]`、`presence?`、`leaderboards?` 按需附带。
- 所有增量仍使用同一 cursor，不新增轮询端点。
- 聊天消息写入服务端长度限制、频率限制和基础审计字段。

验收：
- 两个账号可以通过服务端测试互相看到聊天增量。
- 在线列表能在心跳后显示、超时后消失。
- 排行榜排序稳定，分页或数量上限明确。
- `/game/sync` 无 cursor 首次返回完整必要状态，有 cursor 时只返回增量。
- `sync` 路由保持纯读，不触发世界 tick、任务生成或传闻生成。

不做：
- WebSocket。
- 前端完整大厅视觉打磨。
- 管理端消息删除 UI。

### v0.9.1 大厅面板与聊天交互

目标：玩家能在游戏内看到在线列表、聊天和排行榜，并且键盘/弹层规则不回退。

范围：
- 新增大厅侧栏面板，包含在线、聊天、排行榜 tab。
- 聊天输入接入 `text-entry` 上下文。
- 聊天发送后立即触发一次 sync 拉取。
- 聊天错误显示使用统一 API 错误处理。
- 聊天列表长度和本地渲染数量受控，避免长时间内测后前端卡顿。
- 管理端或服务端提供最小删除能力；若 UI 不做，至少保留受控 service 方法和测试。

验收：
- 两个浏览器账号能互相聊天。
- 聊天输入聚焦时 WASD 不移动。
- 弹层打开时聊天快捷键和移动键不互相踩踏。
- 刷新页面后聊天历史按上限恢复。
- 频率限制和长度限制有明确错误提示。

不做：
- 私聊。
- 聊天频道系统。
- 表情、富文本、图片。

### v0.9.2 广播、排行榜与事件反馈接线

目标：把 v0.8 的刷宝结果和 v0.9 的多人大厅缝在一起，让朋友能看到彼此的高光。

范围：
- 蓝装及以上掉落写入 public `sync_events`。
- 广播进入聊天流或事件流，前端以统一反馈层高亮。
- 玩家升级、关键任务完成可作为低频世界事件写入传闻/广播候选。
- 排行榜面板接入真实同步数据，避免每个面板独立请求。
- 广播 payload 不暴露内部掉落 seed、AI prompt、隐私字段。

验收：
- 蓝装掉落 30 秒内出现在另一个账号的大厅流里。
- 广播不会造成玩家状态重复刷新或重复 toast。
- 掉落广播只来自规则确认后的真实掉落，不允许客户端伪造。
- 排行榜在角色升级或财富变化后能通过 sync 更新。

不做：
- 全服拍卖行。
- 玩家交易。
- 跨地图同屏互动。

### v0.9.3 离线世界报告与 AI 预算熔断

目标：玩家下线后回来能看到世界发生过什么，同时 AI 成本可控、可降级、可审计。

当前状态（2026-07-05）：离线报告、`offline_summary` 边界、每日账号缓存、全局预算熔断、管理端预算展示已完成；NPC 对话开场白记忆增强和更多离线事实源留作 follow-up。

范围：
- 新增 `offline_summary` purpose。
- 规则层选材：`npc_events`、`world_rumors`、市场变化、玩家离线挂机结算、玩家相关高光事件。
- 每账号每日最多生成 1 次 AI 离线报告；其余使用缓存或模板。
- 全局每日 token 预算由 env 配置；超限后自动降级模板并写日志。
- 管理端 AI 状态面板显示预算使用、fallback 次数、最近失败原因。
- NPC 对话开场白引用 `system_verified` 记忆，做态度表达增强，不改权限。

验收：
- 下线 2 小时后登录，能看到包含真实事件的离线报告。
- AI 关闭、超时、预算耗尽时模板报告仍可用。
- `offline_summary` 边界测试通过：不承诺奖励、不编造事实、不 OOC、不写状态。
- 每账号每日限制生效。
- 管理端能看到预算余量和 fallback 状态。

不做：
- AI 自动发奖励。
- AI 自动生成任务。
- AI 修改好感、库存、货币、经验。

## 5. 数据与接口草案

### 5.1 `chat_messages`

最小字段：
- `id`
- `account_id`
- `character_id`
- `channel`：v0.9 只做 `lobby`
- `body`
- `deleted_at`
- `created_at`

索引：
- `(channel, id)`
- `(character_id, id)`
- 删除只做软删除，历史审计保留。

### 5.2 `presence`

优先复用 session 或 character activity 字段：
- `last_seen_at`
- `current_character_id`
- `current_zone_id`

在线判断由规则函数计算，例如 `now - last_seen_at <= 90s`。不要引入常驻 presence worker。

### 5.3 `/game/sync` v0.9 扩展

```ts
type GameSyncDto = {
  cursor: number;
  serverTime: string;
  stateVersion: number;
  state?: GameStateDto;
  events: SyncEventDto[];
  chat?: ChatMessageDto[];
  presence?: PresenceDto[];
  leaderboards?: {
    level?: LeaderboardEntryDto[];
    wealth?: LeaderboardEntryDto[];
  };
  offlineReport?: OfflineReportDto;
};
```

规则：
- `chat` 只返回 cursor 之后或首次同步上限内的大厅消息。
- `presence` 低频附带，可以按服务端节流策略返回。
- `leaderboards` 只在请求参数或服务端间隔满足时附带。
- `offlineReport` 只在登录后首次需要展示时附带，不能每次 sync 都生成。

## 6. 测试策略

必须新增或更新：
- repository/service 单测：聊天写入、频率限制、软删除、排行榜排序、presence 超时。
- `/game/sync` 路由测试：首次同步、游标增量、chat/presence 按需附带、纯读约束。
- 前端测试：大厅面板渲染、聊天输入屏蔽移动、排行榜 tab、广播展示。
- AI 边界测试：`offline_summary` fallback、预算耗尽、禁止奖励承诺、禁止事实注入。
- 端到端或集成冒烟：双账号聊天 + 掉落广播。

版本门禁：

```bash
CI=true pnpm -r test
CI=true pnpm -r typecheck

CI=true pnpm -r build

```

若 `DATABASE_URL` 未配置，真实 Postgres 集成测试可以显式 skip，但必须保留 skip 证据。若本包新增迁移，必须同步 SQL、journal、schema、版本号和迁移验证。

## 8. 推荐第一执行包

下一步应先做 **v0.9.0 同步与大厅数据底座**，理由：

1. 它是 v0.9 后续所有功能的承载层。
2. 它能继续验证 v0.8 的 `/game/sync` 设计是否真的可扩展。
3. 它不依赖 AI，也不改变经济和奖励权限，风险最低。
4. 先打通两个账号的聊天/在线/排行榜，再做 AI 离线报告，验收路径更清晰。

v0.9.0 不通过前，不进入 v0.9.3。AI 报告必须建立在真实事件流和同步入口稳定之后。
