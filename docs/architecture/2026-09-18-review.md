# 架构复核：保留技术栈，先收敛权威边界

日期：2026-09-18。审查源码：`690cbc816051b30e323bb005c93c1396e1303c3c`，产品仍为 `0.10.6`。输入是 `docs/architecture.md` 及实际源码。本文件是静态审查，不是性能测试、完整安全审计、线上事故根因报告或试玩结论。

## 1. 总判断

保留 TypeScript/pnpm workspace、React/Vite、Fastify、PostgreSQL/Drizzle 和模块化单体。问题主要不在品牌选错，而在部分职责仍按开发过程堆叠：事务归属不统一、资产写入口分散、世界推进与读取混合、模型调用治理没有独立统一入口、事实与文案没有彻底分离。

不要推倒重建，不要先开发可复用到任何游戏的通用引擎。下一阶段的目标是：现有玩法不变，也能证明相同的结算和资产约束被所有入口复用。目标设计见 [target.md](target.md)，实施门槛见 [架构基线包](../implementation/2026-09-18/architecture-baseline.md)。

## 2. 架构图的校正清单

原 `docs/architecture.md` 保留作为执行模型提交的现状材料，本 PR 不把它替换成目标图。阅读时必须结合下面的校正，不能把其全部边当成已验证事实。

| 图中表述 | 代码核查 | 应如何理解 |
|---|---|---|
| AI parser 返回“选中 ID + 短理由” | 当前 `npc-task-proposal.ts` 输出 title/description/npcReason/safety；无候选 ID 决策接口 | 这是未来意图方案，不是当前实现；当前任务参数由规则固定，AI 只修饰文案 |
| 每个 service 都由 repo 注入且模块分层统一 | `GameService` 直接注入 Db 并在方法中构造多种 repository/service；task repository 自己管理 transaction；dialogue resource repository 又承担交易用例 | 是分层方向，不是已处处遵守的规则；统一事务和依赖比统一文件名重要 |
| `setInterval` + lease 保证多进程单推进 | acquire 有过期条件，但 saveProgress/releaseLease 只按 key 写，传入的 ownerId 未作为 WHERE 条件 | 不能据此宣称可安全多副本；失效持有者仍有提交/释放通道 |
| 客户端获取增量状态 | `getSync` 实际先锁角色并结算，再按事件决定是否附完整 state；stateVersion = nextCursor | 是“按需结算 + 快照/通知同步”，不是成熟的状态增量复制协议 |
| 离线按时间差批量结算 | 世界 runtime 每分钟迭代，单次受 maxSteps 限制；角色有按需结算 | 世界 catch-up 是有上限的逐 tick 补算，不能写成已经实现任意时长解析式快进 |
| 纯规则包与 DTO 完全隔离 | rules/content 使用 shared 中 GridPositionDto、ItemId 等；combat 规则同时构造中文日志 | 函数纯不等于表现无关，仍需划开领域值与传输/显示类型 |
| AI/任务/关系/记忆归在“AI 层” | 任务状态、可信事件和关系会影响业务，需规则裁决并持久化 | 数据分组可以如此画，但所有权不能交给模型；记忆事实属于 NPC 领域 |

## 3. 需要优先处理的结构问题

### AR-01：世界推进的互斥保证不完整

证据：`apps/server/src/modules/world-runtime/world-runtime.service.ts`（55秒 lease、逐步推进）；`world-runtime.repository.ts`（saveProgress/releaseLease）；`app.ts`（每 tick 的 NPC 更新与进度在同一事务）。

优点：当前每 tick 的更新和进度已在同一事务，不要退化回两次提交。

缺口：租约到期后 A 仍运行，B 获取新租约；A 的 saveProgress 或 releaseLease 仍仅凭 key 写入，可能覆盖 B 的持有信息或进度。`server-${process.pid}` 也不是跨容器唯一身份。本轮没有复现这次序在运行中发生，不据此声称已有重复发工资事故；但防止旧持有者写入的条件在代码中确实不存在。

建议：小型单体优先改为每个 tick 对预建 runtime 行的事务行锁，锁后读取进度、计算下一步、提交全部状态与新进度；锁随事务结束释放。不再维护另一套会过期但无法阻止旧写入的 lease。独立进程级 lease 仅在未来长任务/分区方案确实需要时重新设计。

### AR-02：资产服务并未形成统一写边界

证据：`GameService.buyMarketItem/sellMarketItem`、`NpcTaskRepository.reserveNpcCopper/incrementNpcCopper`、`DialogueResourceTransferRepository.transferNpcCopperToCharacter`、`NpcService` 的资金增减。`LedgerService.recordCopperTransfer` 负责记账，不拥有所有余额变化。

并非这些路径都已出错；问题是未来每多一种 AI 行为就可能多实现一份余额、保留量、账本和幂等处理。统一底层 AssetMutation 入口与显式 tx，任务/市场/NPC 保留业务语义。业务状态、资产、账本、必要事实事件必须同事务；单独成功一份日志不等于资产一致。

物品层已有 ItemService，优先扩展复用。`ItemRepository` 使用 ownsTransaction 布尔值，且接口允许 transaction 缺失时直接执行。建议替换成显式的事务内方法/绑定上下文，让缺少事务不能在生产写路径静默降级。先迁移真实路径，不造一个无人使用的万能服务。

### AR-03：新旧装备表示并存，需明确唯一真源

证据：`GameService.createCharacter` 仍创建 legacy equipment；`GameRepository` 同时有 legacy equipment 与 item_instances 的读取/更新分支。

这可以是迁移阶段的兼容，不应作为永久“两个都权威”。推荐 item_instances 为装备目标真源，迁移现有装备并保留稳定 ID/所有权/属性/耐久；堆叠物品仍可以在 character_items/npc_items/market_inventory 保存，不为形式统一重建大表。

### AR-04：读取、推进和初始叙事的边界混合

证据：`GameService.getSync/getState/settleReadableState`；`game.routes.ts` 初始 sync 调用 offlineReport.getReport；`admin.routes.ts` NPC 快照先推进/ensure seed；`app.ts` 的 WorldPostTickService。

按需结算是适合挂机游戏的策略，本轮不把它简单判成 bug，也不要求先给所有离线角色加高频定时任务。问题是结算逻辑必须只有一个领域入口，纯读取本身应可单独调用。允许外层 sync use case 组合“先按需推进本人、再读快照”，不要把反复读取 DTO 当成结算规则所有者。初始快照不应为了可选模型简报等待完整网络超时。

### AR-05：事实依赖中文展示文本

证据：`GameService.playerDamageFromCombatLog` 用正则读伤害；`TutorialGuide.inferTutorialProgress` 用“移动/采集/返回”识别进度；`CombatTimelineEntry` 只有 atMs/message。

这会让改文案、翻译、换2D表现牵动规则正确性。改为结构化战斗事件与显式里程碑；文字由事件生成，不能反向解析文字生成游戏事实。旧存档需迁移/显式兼容读取，不能静默当作新格式。

### AR-06：API游标不等于领域修订号

证据：`GameService.getSync` 将 stateVersion 设为本页 nextCursor；`useGameSync.ts` 是客户端轮询器。

目标要区分 transport cursor、实体 revision、world epoch。不能把客户端收到的某条事件 ID 当成所有角色/市场/NPC 状态的完整版本；并发响应、分页和重置需要定义。先保持小规模全快照纠偏，不直接升级成复杂 delta replication。

### AR-07：模型接口绑定文本，配置/治理绑定对话

证据：`ai-provider.ts` 只有 completeJson；`createAiOrchestrator` 的全局 enabled 依赖 AI_NPC_DIALOGUE_ENABLED，并把对话超时和输出上限传给多个用途；调用日志分散在 dialogue repository/各个组合器中。

建议独立 DecisionProvider 与 NarrativeProvider，应用级唯一 AiGateway 管理各 purpose 的开关、预算准入、超时和审计。不是声称当前所有调用都没有限制，而是不能从存在一个治理展示面板推定全入口具有统一硬预算。

### AR-08：实例范围需要在新增玩法之前写清

证据：`GameRepository` 的 map instance 有 characterId；`NpcService` 使用共享 worldResourceNodes；市场和NPC为哨站共享状态。

保留“一个共享哨站 + 个人探险实例”可以成立，但必须明示它们是不同资源池。私人地图产出的物资进入公共市场，是可识别的资源来源；不能让AI声称某个玩家清了自己的怪就拯救了全服矿道。改成共享野外是另一个产品变更，不是技术重构。

## 4. 技术选择的复核

- TypeScript/Node 保留；当前没有性能证据要求迁到 Rust/Go，不能从未来可能几百个NPC推导现在要换语言。
- Fastify 5 保留；当前框架不是业务所有权不清的原因。不引入 NestJS/大型依赖注入框架来代替边界设计。
- PostgreSQL 16 + Drizzle 保留；关系型状态、条件更新、唯一约束和短事务适合当前一致性需求。ORM版本升级独立验证，不与结构改造混为一项。
- Node 24 LTS 是下一基线建议；Node 22尚受支持，不将“22+”视为稳定可复现配置。先锁定当前实跑版本和lockfile，单独跑兼容回归再决定升级。
- HTTP轮询保留；低频格子游戏不因2D就必须WebSocket。推送需求出现后更换传输适配器，不重写规则。
- Phaser + React 为浏览器2D默认候选；Godot为转向原生客户端/可视化场景工作流的备选。现在不安装任一引擎。
- 不新增 Redis/Kafka/Temporal/微服务/向量数据库/通用ECS/通用GOAP平台。将来引入任何一个都需瓶颈或具体玩法证据。
