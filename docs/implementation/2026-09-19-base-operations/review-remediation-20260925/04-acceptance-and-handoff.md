## 3. 防止再次漏掉层级问题的试玩方法

1. 每个发现动作前先保存**当前视口**截图，写意图、可见线索和预期。不能先读全页DOM找到按钮再称“首屏可发现”。
2. DOM/可访问树可用来定位已经看见的控件；自动滚动到定位器必须记为工具辅助，不能当玩家自然发现。全页截图用于结构分析，不代表玩家同时看到了整页。
3. 必须滚动时，记录方向、次数、目的及回来需要的操作；特别记录点击上方后反馈是否仍在当前工作区。
4. 固定回归路线与独立新手任务分开。已知道解法的 agent 只能报告熟练视角；真人缺席不声称真人通过。
5. 保存成功、处理中、条件不足、暂停和完成状态的前后证据。计时排除代理读写与工具超时；动态否定断言需要连续证据。
6. 可优先采用无需桌面鼠标的内置浏览器/浏览器协议工具。先实测其截图、输入及同档能力；一种工具锁屏失效不等于产品失败。换工具若不能复用会话，应登记为新存档，不能冒充原档回访。

## 4. 工程验证与交付

执行前读实际 package.json 和测试配置。主线编写时可用：

```sh
pnpm --filter @ai-mud/web test
pnpm --filter @ai-mud/web typecheck
pnpm --filter @ai-mud/web e2e:mock
pnpm arch:check
```

选择与改动相关的测试；web test允许零测试通过，须记录实际用例数。lint若为tsc别名不算独立门槛。公共边界变更再加必要arch/test/build；真实PG和真实浏览器测试先核对DB/端口隔离，避免脚本默认读取.env后连未知生产。不要直接运行可能串起真实服务的总e2e脚本。任何必需项未跑写NOT_RUN与原因。

交付至少包含：精确基线与最终SHA（未提交写明）、文件/API变化、问题ID→验收结果→证据、实际命令/用例数、未解决项与回退方法。集成后更新问题状态和项目摘要；历史发现保留，不覆盖原始失败记录。一个包通过不代表整款游戏或v1.0完整验收通过。
