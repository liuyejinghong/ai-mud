# R1 验收、旧档与交付门槛

本包修复的是用户发现的产品失败。代码测试是必要条件；“新档注册成功、第二项目已开工、页面没有横向溢出”都不是最终完成条件。

## 1. P 的先行检查

| ID | 要验证的默认设计 | 必须证据 |
| --- | --- | --- |
| P01 | 着陆器可自举 | 不借任何已安装设施即可完成第一太阳能；套件、库存和初始能源守恒 |
| P02 | 原料到首扩建 | 正常命令可取得 16 铁矿/4 铜矿，完成 15 批加工与一次维护，再用自产部件建成太阳能；不是 SQL 发料 |
| P03 | 替代路线 | 24 铁矿/4 铜矿能建第二加工间；记录相比能源路线的用电/速度/等待差异 |
| P04 | 恢复 | 全队低电、维护材料用尽、采矿暂停、取消返料都有有成本且可见的恢复路径 |
| P05 | 功耗尺度 | 逐分钟电量账本，无旧 500 Wh 阈值误入新 profile，发电、储能、充电、工厂耗能不重复 |

若首循环不在 30–45 分钟目标附近，先检查是否存在无决策等待/无法发现的入口，再调整工作量或流程。不能通过测试专用高倍率、缩短所有等待到零或赠送材料“达标”。探针只能证明机制可达与预算合理，真人节奏另验。

## 2. 必须真实 PG 验证的不变量

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| G01 | 初始 seed 与重复 provision | 同账号只有一基地；六套件/设备/能源只发一次；所有常设设施未建成 |
| G02 | 设施重复完成/崩溃重试 | 发电/容量/槽位只加一次，材料扣减与建成原子 |
| G03 | 节点并发预留 | 两请求不能超预留/跨基地读写；剩余矿量非负 |
| G04 | 一批开采→送达 | 节点、现场货物、库存守恒，运输前库存不增；相同 ordinal 重放无第二份 |
| G05 | 采矿取消/暂停 | 未采释放；已采送达后结案；暂停可换人并恢复同一进度 |
| G06 | 设备唯一作业 | 一台设备不能同时施工/采矿/运输/充电；旧合作分配不能绕过锁 |
| G07 | item 与 robot 制造 | 单批故障注入全部回滚；重放不重复产出；新造设备零初始电量 |
| G08 | 维护与恢复 | 第 10 批后阻塞第 11 批；一次维护只扣一备件；零备件能通过手工配方恢复 |
| G09 | 时间分片/暂停/隔离 | 1×10 分钟与 10×1 分钟结果相同（按冻结精度）；暂停/另一基地运行不产生收益 |
| G10 | 旧档兼容 | 旧余额/库存/内容版本不改；旧两种配方修订、工程、采购和订单仍能结案 |
| G11 | 新档旧入口 | 直接调用外部购买/接单/交付被拒，不能靠旧 URL 给新档发 credits |
| G12 | 断连/重复命令/旧控制 token | 原 identity 重试只一次效果，旧 token 被拒，状态回读明确 |
| G13 | 整套迁移 | 空库与从当前 schema 33 的副本升级均成功；历史行满足新增条件约束 |

在已知的一次性 PostgreSQL 中跑。根目录 db:* 脚本可能 source .env，不能直接拿未知环境当测试库。使用显式 DATABASE_URL 指向已核实测试实例，报告主机/端口/数据库名但不输出密码。

## 3. 真实浏览器与玩家路径

Q 在同一候选 SHA、同一实际 PG 后端验证，不 mock API，不直接改 DB/系统时钟。每步记录“意图→点击→可见响应→下一步”，关键处截图，保存起止时间和最长等待。

| ID | 路径 | 合格标准 |
| --- | --- | --- |
| U01 | 首访 | 只看页面能说出运抵的东西与未安装的东西；3 分钟内首次施工有可见结果 |
| U02 | 固定工作区 | 1280×800/1440×900 主动作、目标、结果同时可见；长内容局部滚动，没有藏掉关键按钮 |
| U03 | 缺料回路 | 从扩建缺料定位到矿点/配方并开始工作，返回原扩建保留上下文 |
| U04 | 一圈生产 | 亲自勘探→采矿运输→加工→维护→用自产部件扩建完成，页面读得出变化原因 |
| U05 | 再投资三圈 | 不停在首扩建；至少追加一次产能/设备或储能选择，并生产实际消耗的备件，记录每圈的新决定 |
| U06 | 替代路线 | 两新档同天气/货单，先能源与先加工分别测试；能解释取舍，不能只有换个名字 |
| U07 | 同档回访 | 正常离开≥20分钟后回来，生产不补离线收益，目标、队列、在途、库存可接续 |
| U08 | 低电/缺料/维护/断网 | 提示在操作处，给真实恢复行动；不能依赖开发者口头讲解 |
| U09 | 缩放/键盘 | 真 200% 缩放、720×450、键盘首安装与面板返回均可完成 |

30–45 分钟只计算真实前台玩家过程，工具等待与工程调试剔除并另报；未完成就写实际进度。模拟规则回放不能填 U01/U04 的浏览器证据。AI 已读攻略的熟练路线不能充当首访或独立真人。

最终 PLAYTEST_PASS 必须由用户或获授权真人完成目标并理解因果。用户明确说不具备验收条件时，不能引用 CI/评分抵销。AI 可以给“已具备下一次真人验证条件”的有边界建议，不能代签真人通过。

## 4. 必跑命令与容易误用的入口

集成 HEAD 上执行 pnpm -r build、pnpm -r typecheck、pnpm arch:check、pnpm arch:test，以及 CI=true DATABASE_URL=<已核实隔离库> pnpm -r test。一条命令成功与其中测试实际执行是两件事，必须确认新 landing 真 PG 测试没有 skip。

新增 UI 浏览器配置由 I 登记 landing-postgres project，运行 pnpm --filter @ai-mud/web exec playwright test -c playwright.config.ts --project=landing-postgres。这是本包要求新增的目标，当前配置还没有它，不能把它描述成已存在命令。

当前 server e2e:real 的脚本包含旧角色/世界逻辑，不能直接作为 R1 证明。I 可复用其中隔离 PG/端口生命周期逻辑，但新场景只经基地公开 API/UI。mock 项目仅测 UI 行为，单独标 MOCK。

缺浏览器二进制时，先用已安装的合法 browser channel；仍不能启动就报告 NOT_RUN，不能给部署结论。成功跑过的相关门槛不反复扩大重测，除非后续修改或失败带来具体风险。

## 5. 旧测试保留与退役

- 旧 base-0/tutorial-1 行为以显式内容版本 fixture 保留，不把旧 fixture 全改成新默认来隐藏兼容问题。
- 注册默认内容改为 landing-1，原测试中依赖旧默认的场景逐项改为显式旧 profile；变更记录写原断言为何仍应保留。
- 通用鉴权/CSRF/命令幂等/跨基地隔离/离开暂停继续复用。
- 固定要求“开局五设施 built”“UI 必须出现可支配”的新默认测试换为新产品断言；旧内容的五设施断言仍在其版本测试中。
- 测试删减须列出保留/替换/移除原因，不能删失败用例、降低覆盖或改 allowlist 达到绿灯。

## 6. 交付与部署准备

交付包必须有候选 SHA、P 合同、源代码、迁移差异、新旧数据样例、上述 G/U 验收表、失败与修复记录、截图/交互日志、未测项和回退说明。Q 只接受与最终候选一致的证据；修复后仅重跑受影响场景及要求的合并门槛。

本批候选产品版本建议 1.0.2，v1.1 像素路线不动；实施完成时由 I 根据实际主线版本一次性确定。compatibility 递增由实际 schema/API/engine/rules/content/economy/worldSeed 差异决定，prompt 未改不递增；不把文档候选值先写进产品。

合并/部署必须另行取得对应授权。具备授权后才能执行：核对试玩服实际版本/存量 → 备份并校验 → 隔离恢复并演练新迁移 → 同提交构建前后端 → 验证旧档及新档 → 记录发布身份。不得使用 phase0 清档脚本，不批量改变原有基地内容版本，不修改旧账号余额。

部署后的旧档回读要检查账号/基地标识、内容版本、余额、库存、在途与工单；有正常玩家活动时按每档检查点解释变化，不能要求全表哈希永远相同。新档烟测使用明确的一次性账号，按精确 ID 停用并撤销会话；不删除用户数据。

任何“恢复上线前备份”的回退都会影响其后的新进度，必须预先明确恢复点与受影响范围。部署成功不等于本地计划里所有长期经营目标已验收。
