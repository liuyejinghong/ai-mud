# AI MUD 分版本实施总控

文档版本：1.0；编制日期：2026-09-18；状态：PLANNED（仅文档，未实施）。

基线：`90df03d7d771d9ddd0b0b6524b88d9e9aef6333d`，当前产品 `0.10.6`。兼容版本：schema 25 / api 39 / engine 2 / ruleset 16 / content 12 / prompt 8 / economy 4 / worldSeed 1。

## 一、产品目标

把现有 MUD 打磨成：玩家通过冒险、交易与兑现承诺改变居民处境，居民的实际选择又改变玩家机会的小型持续世界。先证明文字版有趣，再验证 AI 相比规则的增益，最后准备像素表现。不是先扩大地图、NPC 数量或模型调用数。

默认产品约束：浏览器优先、TypeScript 全栈、现有 Fastify/PostgreSQL 后端权威、格子探索、自动战斗、四个现有 NPC、食物与矿石两条资源线、小规模受邀内测。首次闭环不依赖付费模型。

## 三、读取与执行方式

1. [执行合同](00-execution-contract.md)：工作切片、实际命令、证据、停止条件。
2. [共享合同](01-shared-contracts.md)：状态归属、事务、事实/叙事、模型输入输出、版本策略。
3. 当前版本包：按任务 ID 顺序执行；每个任务有明确交付与验收。
4. [实施提示词](templates/implementation-prompt.md) 与 [验收模板](templates/evidence-template.md)。

每次给开发模型一个版本，不给它“自行完成整条路线图”的指令。版本内部可以连续完成任务，不必每改一个文件都询问；遇到设计冲突按停止条件提交 deviation，而非自行扩范围。

## 四、两种门槛，不得混为一谈

- ENGINEERING_PASS：源码、迁移、单测、真实数据库并发、必要 E2E 等符合 spec。
- PLAYTEST_PASS：真实玩家能理解取舍、观察因果，并愿意继续游玩。

v0.12.0 即使工程通过，也只能标记 PLAYTEST_PENDING，直到完成其试玩标准。可用便宜的 rules-only 原型验证体验；体验失败优先迭代这一包，不用更贵模型或像素画面掩盖。

v0.14.0 还分 ADAPTER_PASS 与 LIVE_MODEL_GATE_PASS。无密钥、无可靠官方 API 合同、无实际测试记录时不得宣称后者通过。系统可以在 rule 模式继续走后续路径，但不能把“Jev 已接入并验证”列入发行功能。

## 五、不做的事

本轮不做微服务、通用工作流 DSL、全量 Event Sourcing、向量数据库、玩家自由交易、PVP、公会、完整共享野外、无限 NPC、自由生成任务数值、实时动作战斗或自动发布生产。

三种获得矿石路径不等于三个大系统：采集复用原功能，购买复用市场，协商只做一笔有库存的现货交换。信用借贷、承诺未来产出、NPC 物流合同不在首轮。

## 六、证据与设计依据

静态核对范围和外部能力核对限制见 [来源与基线](sources-and-baseline.md)。所有新数值、阈值、玩法回报都是本计划的初始设计值，不是已经调优的结论。只能通过明确的试玩/仿真记录调整，不能由实现模型凭感觉同时改多个系统。

产品版本只在该版本工程验收后更新；完整内测发布还要通过真实玩家与持续运行门槛。不得因为这套文档合并就把 PRODUCT_VERSION 改成未来版本。
