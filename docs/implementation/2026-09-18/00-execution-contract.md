# 00 开发执行合同

适用：执行本目录任意版本包的开发模型。目标是减少临场架构决策，不是要求机械照抄不存在的 API。

## 1. 开工前

读取 AGENTS.md、CLAUDE.md、本总控、共享合同和当前版本包。记录 `git status --short --branch`、`git rev-parse HEAD`、`packages/shared/src/version.ts`。基线之后已有提交时核对本包涉及的路径和前置功能；不得 reset 用户修改，也不得为了回到文档基线删掉新代码。

第一次实施从当前用户授权的开发分支开始。新版本必须以已验收的前一包为基础，而不是每包都从 90df03d 重新分支。并行分支漂移、同一编号已被占用、关键接口消失时先提交差异说明；只停止受影响任务，不伪造旧上下文。

输出一张小表：当前任务 ID、现有符号、拟新增文件、拟修改合同、前置测试结果。每个任务先写失败测试，再实现；纯文档/纯样式任务不强求虚构失败测试。

## 2. 任务执行粒度

- 按当前包的 T01、T02 顺序推进；一个任务一个聚焦提交。测试依赖的小范围修改可同提交。
- 只实现当前包。不能顺手安装 Jev/Phaser、合并所有 NPC 表、改认证、改全仓目录或换 ORM。
- 新文件标记为 NEW，是需要创建的目标，不是声称基线已经存在。现有文件的精确行号可能漂移，以符号与调用链为准。
- 不通过跳过测试、降低断言、扩大候选上限、绕过状态校验让测试通过。
- 不给 mock 套上真实供应商名字充当实测；fixture 输出、规则选择、真实模型调用在日志和报告中必须可区分。
- 采用确定性 clock、seed、固定快照构建测试。不要用 sleep 等待真实几分钟来测试纯规则。

## 3. 已存在的验证命令

以下已在基线 package.json/CLAUDE.md 核对；运行时仍需检查未被后续版本改名：

```bash
CI=true pnpm -r test
CI=true pnpm -r typecheck
CI=true pnpm -r lint
CI=true pnpm -r build
git diff --check
pnpm test:postgres
pnpm db:verify-migrations
pnpm verify:npc-simulation
pnpm --filter @ai-mud/web e2e
```

`lint` 当前实际是 TypeScript 检查，不要把它写成 ESLint 安全审计。真实数据库命令必须使用隔离测试库；先检查连接指向，不输出密码。没有 PostgreSQL、浏览器或凭证时写 NOT_RUN，不能替换成单测后标记原命令通过。

本计划要求新增的 `verify:market-invariants`、`verify:first-journey`、`verify:npc-decisions`、`verify:decision-benchmark`、`verify:scene-contract`、`verify:beta-load` 均不是基线已存在的命令。所属包的任务必须先创建对应脚本与 package.json 入口，再运行。新增脚本全部带 `--help`、显式环境参数、非零失败退出码；不会自动连接/清空默认生产数据库。

## 4. Spec 修改纪律

当前包的产品目标、状态归属、核心公式、事务边界、API 权限是实施约束。遇到冲突记录：事实/证据、影响、最小修订方案、替代方案被拒绝的理由。没有明确批准不得改掉这些约束。

允许的实现细节：局部私有函数名、符合现有命名的测试文件组织、无需新增抽象的辅助函数。新增依赖、表、外部服务，或任务触及不相关模块时必须在报告中解释；任务范围超过文件清单两倍时停止扩张，提交差异而不是继续重构。

发现本包之外的 bug：写后续 finding，不为修它中断已能独立完成的工作；涉及资产丢失、越权或现有测试被当前改动破坏则必须修复/回退当前任务。

## 5. 版本、迁移与发布

运行版本真源只有 `packages/shared/src/version.ts`。新迁移从当前 journal 的实际末尾分配，不硬编码假设 0026 永远空闲；基线末尾为 0025。不可改已执行 SQL。

一个新增迁移必须同步：SQL、Drizzle schema、journal、迁移验证、world reset 范围、备份恢复与版本兼容测试。文档本身不 bump 任何运行版本。

每个版本包给出预期影响域；具体增量以实际兼容语义变更计，不以提交数计。不可为了通过版本断言机械给全部数字 +1。新增数据库内容默认可加不可破坏；跨不兼容版本禁止简单回退旧二进制，先走兼容检查与备份恢复方案。

## 6. 每包交付

必须写 `docs/reviews/<实际日期>-<版本>-acceptance.md`，使用 [证据模板](templates/evidence-template.md)。包括 exact head、完成任务、未完成项、命令与原始结果路径、迁移、开关、成本、已知限制、下一步入口。

工程状态和产品试玩状态分别报告。只有经过实际运行的命令才写 PASS；只读审查写 REVIEWED；人工未参与写 PLAYTEST_PENDING；受外部条件影响写 BLOCKED_EXTERNAL。

版本结束后下一位模型先读这一份交接，不重新猜测哪些功能已做。后续包里的示例接口需要与前包最终落地字段核对，语义不可擅自改变。

## 7. 停止条件

无法建立源/目标库存归属；只能靠模型自由输出数量才实现动作；必须事务内等待网络；没有实际资金却要发奖励；不能区分共享与个人状态；外部 API schema 无可靠来源；测试只能连接生产；或者用户工作树存在会被覆盖的修改。

这些情况输出完成部分和具体阻塞证据。不得伪造 API、默认发币、隐式重置世界或把猜测写入数据库。
