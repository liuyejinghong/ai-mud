# v0.11.0 — 规则与事实地基

状态：PLANNED；前置：当前 v0.10.6 基线核对；输出：修好新玩法会依赖的规则，不增加 AI 或新地图。

## A. 产品 spec

### A1. 用户应感知的变化

市场批量买卖报价可信、确认后不会暗中换价；索要 100 铜币不会被解释成索要 5 铜币；战斗状态和新手进度不会因中文措辞调整而失真。

### A2. 范围

本包只做四项：市场边际计价与写命令幂等；资源请求保留原数量/币种；结构化战斗/采集/移动事件；新手里程碑改为事实驱动。不要顺手重做经济、职业、掉落、战斗系统或整体 UI。

### A3. 市场规则（规范公式）

设交易前库存 S，数量 q，目标库存 T，买入基础价 A，回收基础价 B。有效输入为安全整数：S>=0、q∈[1,999]、T>=1、A>=1、B>=1 且 B<=A。非法输入拒绝，不静默 floor/clamp。税率基点 taxBps∈[0,10000]；首轮保持 500（5%）。

用库存跨越的同一条边 k↔k-1 计算相反方向价格（k>=1）：

```text
r(k)   = T / k
ask(k) = max(1, JS_Math_round(A * clamp(r(k), 0.8, 3)))
bid(k) = min(ask(k), max(1, JS_Math_round(B * clamp(r(k), 0.5, 2))))
BuyGross(S,q)  = sum[i=0..q-1] ask(S-i)             // require q<=S
SellGross(S,q) = sum[i=0..q-1] bid(S+i+1)
Tax(gross)    = ceil(gross * taxBps / 10000)
BuyTotal      = gross + tax
SellTotal     = gross - tax
```

seller 使用 S+i+1，不是 S+i：这样买空一格后卖回同一格，跨越的是同一个库存边界。库存回复原值、无外部变化的任意闭合交易路径，各边 bid<=ask，加上非负税费，不应产生正利润。

不要混淆 `baseBuyPriceCopper`（商店收购价 B）与 `baseSellPriceCopper`（商店卖出价 A）。实现服务适配时一次传入同一商品完整 A/B 数据，不把 direction 字段翻错。NPC 和玩家调用同一个纯报价实现。

返回 `grossCopper/taxCopper/totalCopper/quantity` 与 `effectiveUnitPriceCopper`（展示平均价，不要求整数）；原 `unitPriceCopper` 若必须保留，应明确是首单位参考价，不能再拿它乘 q 作为结算。market_transactions 的准确总额是真源；需要调整列/DTO 时加迁移，不让记录看似单价乘数量却不等于 gross。

测试锚点：旧公式在野莓 S=T=100、A=8、B=5、q=90 下支出756、收入855，净赚99。新公式应买入 gross1434/tax72/total1506；回卖 gross742/tax38/total704；净变化-802。JS Math.round 语义必须保持，不用 Python bankers rounding 生成不同黄金值。

属性测试：买-卖与卖-买、拆单/合单、触及价格上下界、低库存、税费舍入、重复命令。合并与拆分可能因每单税费 ceil 存在差额；断言的是拆分不能制造闭合正收益，不强求两者完全相等。

### A4. 报价确认与去重

新增只读报价入口（建议 `/game/market/quote`），输入 direction/itemId/quantity；返回当前完整总额、库存、报价算法版本。预览不预留库存。

现有 buy/sell 写入请求新增必填 commandId 与 expectedTotalCopper，新客户端及测试同步更新。服务器在原有事务里重新算价；总额变化返回 `QUOTE_CHANGED`，无资产 side effect，UI 显示新报价并让玩家再次确认。若库存变化但价格恰好相同且仍满足数量，可以正常提交；没有必要因无关全局 revision 改变一律拒绝。

NEW `game_command_receipts`：id(UUID primary key)、account_id、command_type、payload_hash、response(JSONB)、created_at。receipt 与资产事务一起提交；插入去重保护并发同 ID。失败回滚不得留下已完成结果；读取 receipt 必须校验 account 与 payload。对超时重试使用相同 ID；新一次确认生成新 ID。这张表不保存未脱敏 prompt。

### A5. 数量解析

`parseNpcResourceRequest` 返回原始正整数请求和规范铜币数，不把上限限制混进解析。明确铜币1/银币100/金币10000，乘法必须通过 Number.isSafeInteger。规范化数量超上限只进入拒绝/部分帮助候选，不丢失原请求。

本包只可靠支持明确正向、单一数量、单一物品/币种的请求；否定、多个数量冲突、多个对象、含糊“随便给点”返回 needs_clarification 或 no_supported_request。不能把“我已有3个，还想要5个”取第一个数字直接转账。原兼容默认1数量只能在 UI明确显示待确认的预览中使用，不可静默转移资产。

本包不做一般自然语言理解。供后续模型使用的语义分类不能替代数量确认。

### A6. 结构化事件与旧活动迁移

先在 simulateCombat 产生伤害的地方保存 actual damage 与 targetHpAfter，再由 formatter 生成人类文本。GameService 使用结构化字段计算已播放血量/取消时损伤，不再调用 playerDamageFromCombatLog。

旧已完成日志只需能显示，不强制重写全部历史。旧 active combat payload 必须在隔离迁移演练中验证：发行切换前停止创建新战斗，按旧规则结算/完成旧 active action 后再切换；无法完成的旧活动需显式可审查的数据转换方案，不能默认归零。此停写/清空“活动队列”的步骤不是删除世界或回收已合法资产。没有兼容证据不得发布新 runtime。

新手进度由明确 `movement.completed`、`gathering.settled`、`inventory.inspected`（非奖励业务，客户端可上报并经服务器拥有权检查）、`village.returned` 等语义更新。开始采集不等于采集完成。进度可存角色对应专用 JSON 列/表，定义 milestone schema；localStorage 只保存展示折叠状态。
